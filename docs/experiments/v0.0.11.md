# v0.0.11 — Family Adapter Registry + Conformance Contract

## Question

Can NEUMANN turn family-specific compilers, solvers, and verifiers into a stable runtime contract instead of hard-coding them into one monolithic engine?

## New contract

Contract version:

`neumann.family.v1`

A family adapter bundles:

- family_id
- IR kind
- compiler
- solver
- answer verifier
- contract version

The registry enforces:

- unique family IDs
- unique executable IR kinds
- no UNKNOWN executable family
- expected compiler / solver / verifier methods
- contract-version compatibility

## Registry engine

The runtime now supports family-owned execution:

raw problem
→ Structure Former
→ IR kind
→ Family Registry
→ family-owned solver
→ family-owned answer verifier

This removes the assumption that every future family must share one global verifier.

## Conformance harness

A family can be tested with:

- valid compile rate
- valid solved+verified rate
- reject fail-closed rate

The goal is to make future family additions measurable against a common contract.

## Important limitation discovered

The current `IRKind` is a Python Enum.

That means a truly external plugin still cannot introduce a new representation kind without modifying NEUMANN core.

Therefore v0.0.11 is **not yet a fully open plugin system**.

This is now an explicit architectural blocker:

> open ecosystem requires an open namespaced kind identifier, not a closed core enum.

## Next question

Can NEUMANN migrate from a closed IRKind enum to namespaced string family / IR identifiers without breaking existing runtime safety and tests?
