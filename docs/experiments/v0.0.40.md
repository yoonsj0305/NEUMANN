# v0.0.40 — Coupled-Block Discovery / Routing Gauntlet

Status: pre-registered research specification

## Motivation

v0.0.38.1 validated a harder mixed Structural Compression family.

The frozen local one-row pipeline:

    target-leaf @ 0.10
        ↓
    deterministic checker
        ↓
    Markowitz residual @ 0.05
        ↓
    deterministic checker

recovered every declared easy leaf on mixed cells and made broad verified
progress, but recovered only about one quarter of total eliminations and about
one third of oracle solver savings.

The exact multi-row reference then removed the remaining coupled 2x2 structure
and reached the declared core.

The next question is no longer whether the mixed family is hard enough.

It is:

> Can NEUMANN discover and route the useful local-vs-coupled structure from the
> observable exact system without generator block identities?

v0.0.40 does **not** train a model.

It first tests whether cheap deterministic structural discovery already solves
the routing problem.

## Fresh family instance

Use the validated v0.0.38.1 generator rules unchanged.

Scale grid:

    k in {2, 4}
    n in {4, 8, 16, 32}
    n >= k

Per cell:

    32 systems

Total:

    256 systems

Use new seeds and a new split label.

Every v0.0.40 signature must be unique within v0.0.40 and disjoint from all
merged comparable corpora through v0.0.38.1.

No generator parameter, oracle leaf identity, oracle block identity, k, or n-k
may be supplied to discovery methods.

## Observable candidate graph

The existing one-row affine enumerator is frozen.

For every visible AffineCandidate define:

    candidate key = (row_index, target)

Discovery methods may inspect:

- original exact coefficients,
- original row indices,
- generic variable names,
- visible one-row affine candidates,
- candidate target incidence across rows.

They may not inspect generator metadata.

## Reference only

The generator-declared easy-leaf and coupled-block identities remain available
only to construct the exact reference and to compute diagnostic discovery
precision/recall after a method has produced its output.

The reference is not available to discovery inference.

## Methods

### M0 — Frozen local-only baseline

Carry forward the v0.0.37 local pipeline unchanged.

Purpose:

    quantify the residual multi-row gap on the fresh set.

### M1 — Target-incidence signature router

Build:

    target -> sorted tuple(rows containing a visible candidate for target)

Routing rule:

- signature length 1 -> route that row/target identity to one-row compression,
- signature length 2 -> group targets by identical two-row signature,
- exactly two targets sharing the same two-row signature -> propose one 2x2
  block candidate for those rows and targets,
- every other signature -> leave unresolved.

No threshold is fitted.

This is the cheapest structured router.

### M2 — Row-pair shared-target router

Build:

    row -> set(targets visible as one-row candidates in that row)

Then:

- targets appearing in exactly one row are routed as one-row leaves,
- for every row pair, compute the intersection of their visible target sets,
- if the intersection contains exactly two targets, derive and validate the
  corresponding 2x2 block candidate,
- select non-conflicting blocks in deterministic row/target order.

No generator identities are used.

### M3 — Exact visible-pair enumerator

Use only the visible one-row candidate universe.

For every unordered row pair:

1. compute all visible targets shared by the two rows,
2. enumerate every unordered target pair from that shared set,
3. derive the exact 2x2 block algebra,
4. retain only candidates whose algebra validates against the original rows,
5. select disjoint candidates by deterministic row/target order.

Targets with visible incidence exactly one are routed as one-row leaves.

This method is intentionally more exhaustive than M1/M2 and serves as the
deterministic search reference.

## Discovered execution

Each method outputs identities only:

- one-row row/target pairs,
- two-row/two-target block pairs.

Execution authority remains with the existing deterministic checkers.

For each method:

1. re-derive every one-row affine rule from the original system,
2. re-derive every 2x2 block rule from the original rows,
3. reject overlapping row or target identities,
4. solve the retained exact system,
5. reconstruct all removed values,
6. verify the ORIGINAL full system,
7. require exact ground-truth equivalence.

No discovered algebra is trusted without re-derivation.

## Primary metrics

For each method report:

- verified retention,
- unsafe accepted reductions,
- final retained dimension,
- final exact solver ops,
- total solver savings,
- oracle solver-savings recovery,
- retained-dimension error relative to the declared core,
- discovered easy-leaf precision/recall,
- discovered block precision/recall,
- unresolved visible candidates.

Discovery-work proxies:

### M1

- visible candidate entries scanned,
- target signatures built,
- two-row signature groups inspected,
- block derivations attempted.

### M2

- visible candidate entries scanned,
- row pairs compared,
- shared-target intersections computed,
- block derivations attempted.

### M3

- visible candidate entries scanned,
- row pairs compared,
- shared-target pairs enumerated,
- block derivations attempted.

Keep discovery-work proxies separate from retained-system solver work.

## Adequacy target

For a deterministic discovery method to be considered adequate on the untouched
final set, all are required:

    verified retention = 1.0
    unsafe accepted reductions = 0
    mean retained-dimension error = 0
    mean oracle solver-savings recovery >= 0.98
    easy-leaf recall >= 0.98
    block recall >= 0.98

Precision is reported and expected to remain exact under the current family, but
the confirmatory runtime objective remains verified downstream solver work.

## Deterministic selection rule

Methods are ordered by expected discovery cost:

    M1 incidence router
        <
    M2 row-pair shared-target router
        <
    M3 exact visible-pair enumerator

Select the first method in that order satisfying the adequacy target.

This ordering is frozen before final data are opened.

## Learned-model gate

No learned block scorer is permitted in v0.0.40.

After final evaluation:

### DELETE_LEARNED_BLOCK_SCORER

If any deterministic method satisfies the adequacy target:

    freeze the smallest adequate deterministic discovery method
    do not train a learned block scorer on this family

### AUTHORIZE_SMALLEST_LEARNED_BLOCK_SCORER

Only if:

    all deterministic methods are safe
    and
    best deterministic oracle solver-savings recovery >= 0.75
    and
    no deterministic method satisfies the adequacy target

Then v0.0.41 may pre-register the smallest learned block scorer.

### REDESIGN_DISCOVERY_REPRESENTATION

If:

    best deterministic solver-savings recovery < 0.75

or safety fails, do not add model capacity.

Redesign the structural representation or family first.

## Routing diagnostic

Report the difference between:

    frozen local-only baseline

and:

    selected discovery/router

in:

- retained dimension,
- solver ops,
- verified solver savings.

This measures the value of routing a visible candidate into the correct
compression primitive instead of treating every candidate as an independent
one-row action.

## KEEP contract

KEEP means the experiment followed the pre-registered contract.

Required:

1. this specification is committed before the first full v0.0.40 result,
2. the v0.0.38.1 generator rules remain unchanged,
3. a fresh disjoint 256-system audit set is used,
4. no discovery method receives generator k, n-k, leaf identities, or block
   identities,
5. M1/M2/M3 algorithms and tie-breaking are frozen before final evaluation,
6. no threshold or method is fitted on final data,
7. all discovered algebra is re-derived from original rows,
8. original full-system verification remains authoritative,
9. every cell contains exactly 32 systems,
10. controls remain unchanged,
11. discovery-work proxies are reported separately from solver work,
12. no learned model is introduced inside v0.0.40.

KEEP does not require deterministic adequacy.

## Expected interpretation

If M1 already satisfies the adequacy target, that is a strong deletion result:

> the current mixed family requires a multi-row compression primitive, but its
> routing/discovery structure is still cheaply identifiable from exact local
> incidence, so learned discovery is unnecessary.

That result would motivate the next harder family to hide block membership while
preserving the same verified local-progress -> multi-row-headroom bridge.

If deterministic discovery leaves real verified headroom, only then is a small
learned discovery model justified.

## Claim boundary

A passing deterministic discovery result would support only:

> on this fresh generated mixed exact-linear family, useful local-vs-coupled
> compression structure can be discovered from observable exact-system
> structure without generator block identities.

It would not establish natural-language Structural Compression, domain
generality, global minimality, total-compute superiority, or the necessity of
learning.
