# v0.0.12 — Open namespaced representation kinds

## Question

Can a third-party reasoning family register and execute through NEUMANN without editing the closed core IRKind enum?

## Compatibility strategy

NEUMANN does not delete IRKind yet.

Instead:

- existing core enums remain valid
- core enums project into the reserved runtime namespace:
  - bipartite_matching → core.bipartite_matching
  - linear_system → core.linear_system
- external families use namespaced string kinds:
  - example.scalar_sum
  - vendor.some_family

The core namespace is reserved.

## Runtime changes

Representation.kind now accepts either:
- legacy IRKind
- open namespaced string kind

The Family Registry is internally keyed by canonical string kind IDs.

This preserves old code while opening the runtime namespace.

## External-family proof

The v0.0.12 test/benchmark defines a dummy external family:

example.scalar_sum

It supplies its own:
- compiler
- solver
- verifier

The test must prove:
1. no IRKind enum member is added,
2. the family registers,
3. RegistryEngine executes it,
4. the answer verifies,
5. the same family conformance harness applies.

## Safety rules

- unnamespaced external kind strings are rejected
- the core.* namespace cannot be claimed by external strings
- unknown remains non-executable
- duplicate canonical kinds are rejected

## What this does not solve

v0.0.12 is a runtime extension contract, not yet a complete plugin distribution system.

Still missing:
- package/plugin discovery
- signed manifests
- permissions/capability declarations
- dependency isolation
- sandboxing
- version negotiation beyond one contract constant
- public registry/index
- supply-chain security

Those should not be papered over by calling the current state a mature plugin ecosystem.
