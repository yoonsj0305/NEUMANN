# v0.0.39 — Coupled-Block Hardness Gate Replication

Status: pre-registered fresh-data replication

## Why this experiment exists

v0.0.38 was methodologically valid:

    KEEP = true

but its pre-registered family decision was:

    FAMILY_NOT_HARD_ENOUGH

because H4 failed.

The other gates passed strongly:

- H1 exact block oracle reached the declared core,
- H2 frozen one-row elimination recovery was far below 0.75,
- H3 frozen one-row solver-savings recovery was far below 0.90,
- H5 the retained-dimension gap was broad across all active cells.

The H4 failure exposed a measurement-definition mismatch.

The intended anti-degeneracy question was:

> does the frozen one-row parser actually see real affine candidates?

The implemented H4 instead measured:

> does the complete old one-row reduction primitive successfully materialize at
> least one accepted reduction?

Those are not equivalent on coupled blocks because the old materializer removes
a selected row/column but does not substitute the eliminated target into its
partner row.

v0.0.39 repairs the gate on **fresh data**.

No v0.0.38 final result is reclassified.

## Frozen structural family

The generator is unchanged from v0.0.38.

Each active derived pair is represented by two exact rows of the form:

    y + z = f(core)
    y - z = g(core)

after:

- random row permutation,
- random column permutation,
- generic variable renaming.

Core and core-side block coefficients retain the same v0.0.38 coefficient
contract.

No cross-block dependencies are added.

## Frozen old pipeline

The v0.0.37 one-row pipeline remains frozen without recalibration:

    target-leaf @ 0.10
        ↓
    deterministic checker
        ↓
    Markowitz residual @ 0.05
        ↓
    deterministic checker

## Frozen exact block reference

The same exact Fraction-based 2x2 block checker from v0.0.38 is used.

Generator metadata supplies only the intended row-pair / target-pair identity.

The checker independently re-derives the exact block algebra from the original
rows and independently verifies the reconstructed answer against the original
full system.

## Fresh audit data

Use the same scale grid:

    k in {2, 4}
    n in {4, 8, 16, 32}
    n >= k

Per cell:

    32 fresh systems

Total:

    256 systems

Use new seeds not used by v0.0.38.

Every v0.0.39 signature must be:

- unique within v0.0.39,
- disjoint from v0.0.38,
- disjoint from all comparable prior generated signatures.

The final set is opened only after this specification and implementation are
committed.

## Unchanged gates

### H1 — Oracle reaches the declared core

Over active systems:

    mean block-oracle retained-dimension error = 0

### H2 — Old one-row elimination remains materially incomplete

Over active systems:

    mean one-row elimination recovery <= 0.75

### H3 — The structural gap matters computationally

Over active systems:

    mean one-row solver-savings recovery <= 0.90

### H5 — Multi-row value is broad

At least 5 of the 7 active scale cells must satisfy:

    mean retained_dimension_gap
        >= 0.5 * block_count

where:

    block_count = (n - k) / 2

H1, H2, H3 and H5 are unchanged from v0.0.38.

## Repaired H4 — Direct candidate visibility

The old H4 is not reused.

The anti-parser-blindness condition is now measured directly.

For every active example:

    expected one-row affine candidate count
        = 4 * block_count

because each of the two block rows exposes either member of the derived pair as
a unit-coefficient affine target.

Required:

### H4a — Candidate count exact

    100% of active examples satisfy:
        enumerated one-row candidates
            = 4 * block_count

### H4b — Candidate algebra valid

    100% of enumerated one-row candidates pass
    validate_candidate_against_system(original_system, candidate)

These conditions directly test parser/algebra visibility.

They do not require the old materialization primitive to accept a candidate.

## Descriptive old-pipeline progress

The following is still reported:

    active examples with accepted one-row eliminations > 0

but it is **not** a confirmatory hardness gate in v0.0.39.

Reason:

successful materialization depends on the expressive power of the frozen
one-row reduction primitive, not merely on whether the local affine structure
is visible.

## Family decision

If safety passes and all of:

    H1
    H2
    H3
    H4a
    H4b
    H5

pass on the fresh set:

    family_status = HARDER_FAMILY_VALIDATED

If safety passes but any gate fails:

    family_status = FAMILY_NOT_HARD_ENOUGH

If safety fails:

    family_status = INVALID_FAMILY_OR_CHECKER

No thresholds or gates may be changed after the v0.0.39 final set is opened.

## Safety contract

Required:

    full baseline verified retention = 1.0
    frozen one-row pipeline verified retention = 1.0
    exact block reference verified retention = 1.0
    unsafe accepted one-row reductions = 0
    unsafe accepted block reductions = 0

No-compression controls must remain unchanged.

## KEEP contract

KEEP means the fresh replication was executed according to the pre-registered
contract.

Required:

1. specification committed before first v0.0.39 full result,
2. generator implementation unchanged except new split/seed plumbing,
3. block checker implementation unchanged,
4. old one-row thresholds remain exactly 0.10 / 0.05,
5. fresh signatures are disjoint from v0.0.38 and prior comparable corpora,
6. all eight cells contain exactly 32 systems,
7. H4a/H4b are computed directly from the one-row candidate enumerator and
   algebra validator,
8. original full-system verification remains authoritative,
9. no final result changes a threshold, gate, or implementation,
10. cost layers remain separately reported.

KEEP does not require the family gate to pass.

## What a pass would mean

A passing v0.0.39 would support only:

> on a fresh generated coupled-block exact-linear family, the frozen one-row
> parser sees the intended local affine candidates, yet the frozen one-row
> Structural Compression primitive leaves a broad verified computational gap
> that an exact two-row block primitive can remove.

This would validate the family as a harder Structural Compression testbed.

It would **not** establish learned block discovery.

## Next milestone if validated

Only after:

    HARDER_FAMILY_VALIDATED

may the next version test block discovery.

The first discovery experiment must compare:

1. deterministic exact 2x2 row-pair / target-pair enumeration,
2. sparse row-pair heuristics,
3. graph / connected-component pairing,
4. a learned block scorer only if cheaper deterministic methods leave
   pre-registered downstream headroom.

The optimization target remains:

    verified downstream solver work

not generator block-label imitation.

## Claim boundary

v0.0.39 is a confirmatory family-validation replication.

It makes no claim about:

- neural superiority,
- natural-language Structural Compression,
- domain generality,
- global minimality,
- total-compute superiority,
- asymptotic improvement.


## First-run implementation freeze

Before the first v0.0.39 full result is observed:

- the fresh-data seed family is frozen,
- H1/H2/H3/H4a/H4b/H5 are frozen,
- the old one-row thresholds are frozen,
- the block checker is unchanged from v0.0.38,
- no learned model is present.

Any post-result change requires a new version and fresh data.
