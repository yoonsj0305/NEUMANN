# v0.0.19 — Out-of-Process Plugin Execution Boundary

## Question

Can NEUMANN execute external compiler/solver/verifier code outside the core Python process while preserving authorization, fail-closed behavior, and the existing Family Adapter contract?

## Architecture

Core process:
- static manifest
- authorization ledger
- ManagedPluginRegistry
- RegistryEngine
- JSON RPC proxy

Child process:
- plugin import
- adapter factory
- compiler / solver / verifier operation

The plugin module is never imported into the parent/core Python process on the out-of-process path.

## Protocol

Protocol version:
`neumann.plugin.rpc.v1`

Transport:
- child process stdin/stdout
- JSON request/response
- request size limit: 64 KiB
- response size limit: 256 KiB
- operation timeout

Supported operations:
- compile
- solve
- verify

Each operation runs in a fresh child process in this prototype.

## Authorization

Authorization is checked immediately before every subprocess creation.

Therefore:
- revoked compiler request launches no child
- ManagedPluginRegistry still checks authorization before solver dispatch
- exact manifest identity remains authoritative

## Fail-closed behavior

- compiler dispatch timeout/crash → UNKNOWN
- solver timeout/crash → failed SolveResult
- verifier timeout/crash → failed SolveResult
- invalid protocol → failed operation

## Containment proof target

The tests prove:
- plugin module absent from parent `sys.modules` before and after execution
- child worker PIDs differ from parent PID
- child environment mutation does not mutate parent `os.environ`
- timeout/crash does not become a verified answer
- revocation prevents the next child launch

## Critical boundary

**This is process separation, not a security sandbox.**

The child process still runs:
- as the same OS user
- with inherited filesystem permissions
- with normal process/network capabilities unless constrained elsewhere

A malicious plugin may still affect the host, spawn descendants, read/write accessible files, or use the network if the OS permits it.

v0.0.19 only removes direct shared-memory/Python-runtime coupling between plugin code and NEUMANN core and creates a killable RPC boundary.

Future isolation work may require OS-level sandboxing, containers, seccomp, namespaces, job objects, restricted tokens, or a separate service boundary depending on platform and threat model.
