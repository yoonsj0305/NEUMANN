# v0.0.23 — Worker State Declaration + Lifecycle Classes

## Question

Can NEUMANN map plugin-declared state semantics to enforceable worker lifecycle behavior instead of relying on one global recycling threshold?

## Manifest extension

`PluginManifest v1` gains an optional backward-compatible `state_class` field.

Legacy manifests that omit the field preserve their previous canonical dictionary shape and digest.

When present, `state_class` becomes part of the canonical manifest and therefore part of the SHA-256 approval identity.

Changing the state declaration therefore requires a new approval.

## State classes

### `stateless_semantics`

Meaning:
- correctness must not depend on hidden worker state
- retained caches/implementation details must not change semantics

Runtime:
- persistent worker allowed
- no mandatory count-based recycle imposed by this class alone

### `cache_only`

Meaning:
- retained state may be used only as a performance cache
- semantics must remain reconstructible from explicit request/artifact

Runtime:
- persistent worker allowed
- **finite `max_requests_per_worker` is mandatory**
- missing finite recycle policy is rejected

### `explicit_stateful`

Meaning:
- semantics intentionally depend on state that spans requests/sessions

Runtime in v0.0.23:
- **REJECT**

Reason:
NEUMANN does not yet have a session-scoped explicit state protocol. Running such a family as ordinary persistent or fresh-process code could silently violate its semantics.

### `non_persistent_only`

Meaning:
- plugin explicitly forbids worker reuse

Runtime:
- fresh process per operation

### declaration absent

Runtime:
- fresh-process fail-safe for the declaration-aware builder

This preserves compatibility while avoiding an assumption that a legacy plugin is safe to persist.

## Claim boundary

A state-class declaration is a contract claim by the plugin, not formal proof.

A malicious or buggy plugin can lie about being `stateless_semantics`.

Runtime enforcement controls lifecycle behavior, but declaration conformance still requires tests/verification.

## Security boundary

State classes govern worker reuse and semantic-state risk.

They do not provide:
- filesystem isolation
- network isolation
- side-effect rollback
- publisher authenticity
- hostile-code sandboxing
