# v0.0.23 — Worker State Declaration + Lifecycle Classes

## Question

Can NEUMANN replace one global persistent-worker policy with a plugin-declared lifecycle class that the runtime actually enforces?

## State classes

### STATELESS
Semantic correctness requires no retained worker state.
Persistent reuse is permitted, but hidden state is never semantic authority.

### CACHE_ONLY
Retained state may improve performance, but clearing it must not change semantic results.
Persistent reuse is permitted.

### STATEFUL_EXPLICIT
State is part of the family semantics and must eventually be represented by an explicit state-transfer/checkpoint protocol.

v0.0.23 does **not** implement such a protocol, therefore both current fresh-per-operation and persistent builders fail closed for this class.

### NON_PERSISTENT
The family may execute only through a fresh-process path.
Persistent-worker construction is rejected.

## Legacy manifests

Older manifests without `worker_state_class` remain compatible with the fresh-process execution path.

They are **not** allowed to opt into persistent reuse implicitly.

This preserves backward compatibility while making the stronger reuse privilege explicit.

## Identity rule

When declared, `worker_state_class` is part of the canonical manifest and therefore part of its SHA-256 approval identity.

Changing a plugin from NON_PERSISTENT to CACHE_ONLY, for example, changes the manifest digest and requires a new approval.

## Enforcement target

The runtime must reject incompatible combinations before launching plugin code:
- undeclared + persistent → reject
- NON_PERSISTENT + persistent → reject
- STATEFUL_EXPLICIT + current execution builders → reject
- STATELESS + persistent → allow
- CACHE_ONLY + persistent → allow

## Boundary

A declaration can be dishonest.

v0.0.23 enforces compatibility between the declaration and the selected lifecycle, but it does not prove a plugin that declares CACHE_ONLY actually obeys cache-only semantics.

That still requires conformance probes such as the v0.0.22 cross-generation and poison-state tests.

## Main finding

> **Persistent reuse is now an explicit manifest-level privilege rather than an implicit runtime default.**

The runtime can reject incompatible lifecycle choices before launching plugin code.

## Backward-compatibility decision

Legacy manifests without a lifecycle declaration keep the safer capability:

`fresh-process execution`

but do not silently inherit the stronger privilege:

`persistent worker reuse`

This preserves old packages while making reuse opt-in.

## Approval identity consequence

`worker_state_class` is part of the canonical manifest when declared.

Therefore a lifecycle-class change is also an authorization-identity change.

For example:

`CACHE_ONLY → NON_PERSISTENT`

requires a newly approved manifest digest.

## Important negative boundary

The runtime can enforce what a plugin **declares**, but it cannot infer whether that declaration is honest.

A plugin that claims `CACHE_ONLY` may still accidentally depend on hidden mutable state.

Therefore lifecycle class enforcement is only one side of the contract:

`declaration + behavioral conformance evidence`

v0.0.22 cross-generation/state-hygiene tests remain the behavioral counterpart.

## Decision

**KEEP**
- explicit lifecycle declarations
- persistent reuse as opt-in privilege
- legacy fresh-only fallback
- STATEFUL_EXPLICIT fail-closed until a real state protocol exists
- lifecycle class bound into manifest digest

## Next candidate milestone

The next missing piece is not another class.

It is **behavioral attestation for the declared class**:

> Can NEUMANN automatically test whether a plugin that declares STATELESS or CACHE_ONLY actually behaves consistently across worker recycle/generation boundaries?

Candidate v0.0.24:
**Lifecycle Conformance Attestation**

Possible gates:
- repeat same corpus across warm/recycled generations
- compare semantic outputs independent of PID/cache metadata
- poison/reset probes where supported
- produce attestation evidence bound to plugin manifest digest
- refuse persistent privilege when attestation is absent or stale

This would connect declaration to measured evidence instead of trusting manifest metadata alone.
