# v0.0.15 — Cross-Package Interoperability Proof

## Question

Can NEUMANN core and an external reasoning family operate as separate Python distributions inside a fresh environment?

## Stronger evidence target

Previous versions proved:
- external namespaced family IDs can exist
- manifests can be discovered statically
- activation can be explicit

But the external family was still constructed inside benchmark code.

v0.0.15 packages the external family as its own Python wheel:

neumann-example-scalar-sum

The core and plugin are then installed into a new virtual environment.

## Interoperability flow

1. build NEUMANN core wheel
2. build external plugin wheel
3. create fresh virtual environment
4. install both distributions
5. start a new Python process
6. verify plugin module is not imported
7. statically discover manifest from installed distribution metadata
8. build catalog
9. explicitly activate plugin
10. verify import occurs only at activation
11. register FamilyAdapter
12. execute raw problem through RegistryEngine
13. run family conformance
14. verify result and trace

## External package

The test package contains:
- its own pyproject.toml
- its own package namespace
- static NEUMANN manifest
- compiler
- solver
- verifier
- adapter factory

It does not modify core IRKind or core source at runtime.

## Claim boundary

The two artifacts are separate Python wheel distributions and are tested in a fresh venv.

However, the external package source still lives under the same Git repository because the current GitHub connector cannot create a second repository.

Therefore this is:
- real cross-distribution evidence
- real installed-package discovery evidence

but not yet:
- independently maintained repository evidence
- independently published PyPI interoperability
- publisher trust / signature evidence
- sandbox or dependency-isolation evidence
