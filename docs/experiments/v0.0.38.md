# v0.0.38 — Coupled-Block Harder Structural Family Gate

Status: pre-registered research specification

## Motivation

v0.0.37 saturated the original generated affine-linear family.

A 193-scalar state-aware MLP recovered most one-step greedy residual utility,
but the validation-selected deterministic Markowitz residual policy was simpler
and better on untouched final data.

The next experiment therefore does **not** add model capacity.

It changes the structural family.

The target failure mode of the old family was:

> useful elimination structure was too visible to one-row sparsity and incidence
> statistics.

v0.0.38 introduces a structural primitive that cannot generally be completed by
independent one-row affine eliminations.

## New compression motif: coupled 2x2 blocks

For each pair of derived variables y and z, generate two exact constraints of
the form:

    y + z = f(core variables)
    y - z = g(core variables)

after row/column permutation and generic variable renaming.

Each individual row permits a valid one-variable affine elimination such as:

    y = f(core) - z

but the two one-row rules form a dependency cycle if both y and z are removed
independently.

A joint 2-row / 2-target solve instead yields:

    y = (f + g) / 2
    z = (f - g) / 2

and can eliminate both variables while retaining only the core variables.

This creates a genuine distinction between:

    local one-row elimination

and:

    multi-row structural compression.

## Family construction

Use the existing scale grid:

    k in {2, 4}
    n in {4, 8, 16, 32}
    n >= k

For every active cell n > k:

    block_count = (n - k) / 2

which is integral for the frozen grid.

Each system contains:

1. a dense strictly diagonally dominant k x k core,
2. block_count independent coupled 2x2 derived-variable motifs,
3. random bounded integer core-to-block coefficients,
4. random bounded integer ground-truth values,
5. row permutation,
6. column permutation,
7. generic variable names v0...v(n-1).

Derived blocks may depend on core variables only in v0.0.38.

Cross-block dependencies are deferred to a later experiment.

## Why this is not a parser-failure benchmark

The old one-row candidate enumerator must still see valid candidates in each
coupled block.

Every block row has unit coefficients on both derived variables.

Therefore the frozen one-row pipeline is allowed to make real compression
progress.

The intended hardness comes from the fact that independent one-row rules cannot
remove both members of a coupled pair without creating a reconstruction cycle.

## Frozen old-family baseline

Carry forward the exact v0.0.37 deployable pipeline without recalibration:

    target-leaf @ 0.10
        ↓
    deterministic checker
        ↓
    Markowitz residual @ 0.05
        ↓
    deterministic checker

No final or v0.0.38 data may tune these thresholds.

This baseline uses only the existing one-row AffineCandidate primitive.

## New exact block reference

v0.0.38 adds a machine-checkable BlockCandidate primitive containing:

- exactly two source row indices,
- exactly two eliminated targets,
- exact Fraction-valued affine reconstruction rules for both targets.

For candidate row pair R and target pair T:

    B * T + D * X = b

where B is the exact 2x2 target coefficient matrix.

The checker requires:

    det(B) != 0

and derives:

    T = B^{-1} (b - D X)

using exact Fraction arithmetic.

A candidate is accepted only if:

1. row indices are in range and distinct,
2. target variables are in range and distinct,
3. its reconstruction algebra exactly matches the original rows,
4. accepted block candidates use disjoint row sets,
5. accepted block candidates use disjoint target sets,
6. block reconstruction dependencies are acyclic,
7. the retained square system solves exactly,
8. reconstruction verifies the ORIGINAL full problem,
9. reconstructed values match the declared ground truth.

The checker, not generator metadata, remains execution authority.

## Oracle boundary

The generator records the intended row-pair / target-pair blocks.

v0.0.38 may use those intended block identities to construct the exact oracle
reference.

This is a **family hardness / primitive sufficiency gate**, not a block-discovery
experiment.

No claim is made that NEUMANN can yet discover the correct block pairs.

That discovery problem is reserved for v0.0.39 if this gate passes.

## Core ratios

For active n > k examples:

    oracle_elimination_count = n - k

    one_row_elimination_recovery
        = one_row_accepted_eliminations
          / oracle_elimination_count

    oracle_solver_savings
        = baseline_solver_ops - block_oracle_solver_ops

    one_row_solver_savings
        = baseline_solver_ops - one_row_solver_ops

    one_row_solver_savings_recovery
        = one_row_solver_savings
          / oracle_solver_savings

    retained_dimension_gap
        = one_row_retained_dimension - k

## Pre-registered harder-family gate

The family is retained for v0.0.39 only if all safety conditions pass and the
following aggregate conditions hold over active cells:

### H1 — Oracle reaches the declared core

    mean block-oracle retained dimension error = 0

### H2 — Old local pipeline is materially incomplete

    mean one-row elimination recovery <= 0.75

### H3 — Incompleteness matters computationally

    mean one-row solver-savings recovery <= 0.90

### H4 — Old pipeline still makes real progress

    fraction of active examples with
    one-row accepted eliminations > 0
        >= 0.75

This prevents the experiment from being counted as hard merely because the old
candidate parser sees nothing.

### H5 — Multi-row value is broad, not one-cell-only

At least 5 of the 7 active scale cells must have:

    mean retained_dimension_gap >= 0.5 * block_count

where:

    block_count = (n - k) / 2

    family_status = HARDER_FAMILY_VALIDATED

    family_status = FAMILY_NOT_HARD_ENOUGH

## Diagnosis

The H4 failure is not parser blindness.

Every active cell exposes the expected local affine alternatives:

    mean candidate count = 4 * block_count

The failure occurs because each coupled target also appears in the partner row.
An independent one-row removal therefore usually fails the full sufficiency
check unless the remaining equations happen to stay valid for that concrete
instance.

This reveals a real primitive boundary:

    locally valid affine identity
        !=
    globally sufficient independent one-row reduction

The exact 2x2 block primitive safely crosses that boundary and reaches the
declared core on every active system.

## Why H4 is not weakened

The anti-parser-blindness intent could be tested by candidate visibility alone.

However the frozen H4 is stronger:

> the old cheap pipeline must make actual safe progress before the new
> multi-row primitive becomes necessary.

That stronger requirement is useful.

Changing H4 to visibility would make the next benchmark easier to pass and
would discard information learned from v0.0.38.

Therefore H1-H5 remain unchanged.

## Required redesign

Do not tune thresholds.

Do not train a block-discovery model yet.

Use a fresh mixed-motif family:

### Smallest active cell

For n-k = 2:

    one pure coupled block

### Larger active cells

For n-k >= 4:

    exactly 2 easy one-row leaf variables
        +
    (n-k-2)/2 coupled 2x2 blocks

Easy leaves must:

- use unit target coefficients,
- depend only on core variables,
- appear in exactly one row,
- be safely removable by the frozen one-row pipeline.

Coupled variables retain the v0.0.38 two-row motif.

This creates the intended trajectory:

    cheap local compression makes real progress
        ↓
    local primitive saturates
        ↓
    coupled structure remains
        ↓
    multi-row compression is required

The original H1-H5 thresholds remain unchanged.
