# v0.0.26 — Structural Efficiency Measurement Contract

## Question

Can NEUMANN demonstrate a real, measurable benefit from making structure a reusable intermediate asset before claiming broader compute efficiency?

## Why this milestone exists

By v0.0.25 the runtime, plugin, authorization, lifecycle, and evidence substrate had become much stronger than the original research core.

That created a project risk:

> NEUMANN could keep improving infrastructure without testing the hypothesis that motivated the project.

v0.0.26 therefore returns to the central idea:

    raw problem
      → solver-ready structure
      → deterministic execution
      → verification

and asks whether the structure itself can be reused as computation.

## Paired experiment

For one valid problem and family adapter, compare two modes over the same number of repeated executions.

### Mode A — compile every time

For every repetition:

    raw text
      → compiler
      → representation
      → solver
      → verifier

### Mode B — compile once, reuse structure

Once:

    raw text
      → compiler
      → representation

Then repeat:

    same representation
      → solver
      → verifier

The answer and verification behavior must remain equivalent.

## Measurement contract

v0.0.26 records:

- raw UTF-8 text bytes
- canonical solver-relevant representation bytes
- representation / raw byte ratio
- representation steps
- solver steps
- verification steps
- fallback steps
- verified rate
- paired answer equivalence rate
- representation identity stability
- wall-clock time

### Canonical representation byte accounting

The byte proxy contains only:

- canonical kind ID
- solver-relevant payload

It deliberately excludes:
- confidence
- rationale text

because those are not consumed by the deterministic solver.

## What each metric means

### representation_steps

A NEUMANN instrumentation count.

It is **not**:
- FLOPs
- CPU instructions
- GPU operations
- joules

### serialized bytes

A deterministic interface-size proxy.

It is **not**:
- tokenizer output
- context-window usage
- memory bandwidth actually transferred

### wall-clock time

A directly measured runtime diagnostic on the CI host.

It is **not** used as a keep gate because small Python workloads are noisy and hardware-dependent.

## Pre-registered keep gate

Use **8 repetitions** in the benchmark.

KEEP the measurement contract only if every fixture satisfies:

1. compile-every-time verified rate = **1.0**
2. compile-once-reuse verified rate = **1.0**
3. paired answer equivalence rate = **1.0**
4. repeated compilation emits a stable canonical representation
5. compile-every-time representation steps = **8**
6. compile-once-reuse representation steps = **1**
7. solver steps are identical between modes
8. verification steps are identical between modes

No keep criterion requires the representation to be smaller than the raw text.

A representation/raw byte ratio above 1.0 is a valid negative result and must be reported.

No keep criterion requires wall-clock speedup.

## Fixtures

The initial benchmark uses four small deterministic fixtures:

- 3-item bipartite matching
- 5-item bipartite matching
- 2-variable linear system
- 3-variable linear system

This is intentionally narrow.

## Expected exact structural result

With 8 repetitions and a deterministic one-step family compiler:

    compile every time representation steps = 8
    compile once reuse representation steps = 1

Therefore, if the contract behaves as designed:

    representation-step reduction factor = 8.0

This is an instrumented amortization fact, not an 8x end-to-end compute claim.

Solver and verification work should remain unchanged because v0.0.26 deletes only repeated representation formation.

## Failure interpretations

### If answers differ

Structural reuse is semantically unsafe in the tested family.

### If solver / verification steps differ

The supposedly reusable representation is changing downstream work and the comparison is not isolated.

### If representation identity changes

The compiler is not deterministic enough for this reuse contract.

### If representation bytes exceed raw bytes

Structure is not acting as a compression format for that fixture. The reuse result may still be valid.

### If wall-clock is slower

The current Python representation layer has overhead larger than the eliminated compile work at this scale. Record it rather than hiding it.

## Boundary

This experiment does **not** establish:

- small-model vs frontier-model parity
- LLM token savings
- GPU memory reduction
- energy efficiency
- broad natural-language structural reasoning
- OOD generalization
- 10x end-to-end speedup

It establishes only whether a verified solver-ready representation can be measured and reused as a stable intermediate computation on controlled fixtures.

## Next milestone candidate

If v0.0.26 passes, the next experiment should move one layer closer to the central model hypothesis.

Candidate v0.0.27:

**Model-Side Structural Proposal Cost Benchmark**

Compare, on a fixed corpus:

    direct learned prediction / solution attempt

against:

    small learned structural proposal
      → deterministic compiler
      → solver
      → verifier

with explicit accounting for:
- model feature/input size
- confidence / abstention
- task accuracy
- false-route rate
- representation byte size
- CPU time
- model parameter count where available

The project should not claim LLM-scale efficiency until an actual language model is placed under the same paired measurement contract.
