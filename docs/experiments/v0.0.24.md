# v0.0.24 — Lifecycle Conformance Attestation

## Question

Can NEUMANN require measured behavioral evidence before granting a plugin persistent-worker privilege?

## Motivation

v0.0.23 introduced lifecycle declarations, but a declaration is only metadata.

A plugin can claim `CACHE_ONLY` or `STATELESS` and still accidentally depend on hidden worker state.

v0.0.24 therefore separates:

`declaration`

from:

`attested behavior`

## Privilege model

Public persistent execution now requires both:

1. exact-manifest authorization
2. exact-manifest PASS lifecycle attestation

Conceptually:

`manifest declaration + authorization + behavioral attestation → persistent privilege`

Attestation is bound to the exact canonical manifest SHA-256.

A changed manifest does not inherit old evidence.

## Conformance-only execution path

An attestation cannot be created if persistent privilege is required before the candidate can be tested.

Therefore v0.0.24 introduces an internal conformance-only builder.

It still enforces:
- manifest validation
- exact-manifest authorization
- activation policy
- persistent-compatible lifecycle class
- out-of-process execution

but bypasses only the attestation requirement long enough to measure the candidate.

It is deliberately not exported as a public runtime API.

## Pre-registered minimum gate

Before observing CI results, PASS requires:
- at least **3** conformance cases
- at least **2** warm repetitions per case
- warm persistent mode: all checks pass
- recycled mode: all checks pass
- compile/solve/verify cross-generation mode: all checks pass
- semantic expected-subset equivalence rate: **1.0**

This is a minimum prototype evidence gate, not a formal proof or universal certification standard.

## Execution modes

### Warm
Same persistent worker is reused across repeated cases.

### Recycled
Worker is recycled at case boundaries.

### Cross-generation
`max_requests_per_worker=1` forces compile, solve, and verify across distinct generations.

## Attestation identity

Attestation records include:
- attestation version
- exact manifest SHA-256
- plugin ID
- declared worker state class
- conformance corpus SHA-256
- case count
- warm repetition count
- mode pass/fail results
- semantic equivalence rate
- generation counts
- failure reasons

The attestation itself has a canonical SHA-256 digest.

## Runtime behavior

Public persistent builder:
- no attestation registry → reject
- no exact-manifest attestation → reject
- stale attestation for same plugin ID/different digest → reject
- FAIL attestation → reject
- exact PASS attestation → allow

## Boundary

Passing a finite conformance corpus does not prove lifecycle semantics for all possible inputs.

v0.0.24 attestation is:

> deterministic, exact-artifact behavioral evidence over an explicit test corpus.

It is not:
- formal verification
- proof against malicious adaptive behavior
- publisher identity
- OS sandboxing
- durable remote attestation storage

The attestation registry is in-memory in v0.0.24.

## Main finding

> **Persistent reuse can now be conditioned on measured behavior of the exact approved plugin artifact, rather than on lifecycle metadata alone.**

The authorization chain is now conceptually:

`exact artifact → explicit lifecycle declaration → behavioral attestation → persistent privilege`

Changing the manifest breaks both the authorization identity and the attestation identity.

## Evidence strength

The attestation adds a materially stronger evidence layer than v0.0.23, but it remains finite-corpus evidence.

It demonstrates that the tested artifact preserved expected semantic outputs under:
- warm hidden-state reuse
- case-boundary recycling
- compile / solve / verify generation separation

It does not establish correctness outside the declared corpus.

## Decision

**KEEP**
- exact-manifest attestation identity
- corpus digest
- attestation digest
- minimum evidence gates
- internal conformance-only bootstrap path
- public persistent gate requiring PASS evidence
- stale/FAIL/missing attestation rejection

## Next candidate milestone

The largest new weakness is that the attestation registry is process-local memory.

Recommended next question:

> **Can lifecycle attestations become durable, auditable, revocable evidence without turning a stale PASS into permanent authority?**

Candidate v0.0.25:
**Durable Attestation Ledger + Use-Time Evidence Revocation**

Possible requirements:
- persisted canonical attestation records
- exact manifest + corpus + attestation digest identity
- ACTIVE / REVOKED evidence state
- use-time attestation check before every persistent dispatch or generation start
- restart persistence
- stale/revoked evidence fail closed
- append-only/tamper-evident history aligned with the authorization ledger

Do not treat a historical PASS as permanent authority if its evidence has been revoked or superseded.
