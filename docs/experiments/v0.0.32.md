# v0.0.32 — Structural Compression Contract + Oracle Lower Bound

Status: pre-registered research specification

## Purpose

v0.0.32 is the first experiment whose primary variable is **compression of computational degrees of freedom** rather than routing quality.

It should not begin by training a learned compressor.

First establish a trustworthy measurement contract and an oracle lower bound on a controlled family where the true reducible structure is known by construction.

## Core family

Use generated exact linear systems with a small independent core and many explicitly dependent variables.

Example:

    core variables:
        x1, x2, x3

    derived variables:
        u1 = 2*x1 - x2
        u2 = x1 + x3
        u3 = 3*u1 - u2
        ...

The raw system is constructed so that all variables have unique values and the full system can be solved directly.

The generator also retains the ground-truth dependency DAG used to create the system.

This gives three structures:

1. **Raw full system**
2. **Oracle-compressed core**
3. **Reconstruction map from core to eliminated variables**

The ground-truth dependency graph is evaluation metadata only. It must not be exposed to any future learned compressor at inference time.

## Required scale grid

Pre-register multiple apparent dimensions while controlling core dimension.

Initial proposal:

    core dimension k ∈ {2, 4}
    apparent dimension n ∈ {4, 8, 16, 32}
    systems per cell = fixed constant

At minimum, include families where:

    n grows
    k stays fixed

so the experiment can test whether solver work follows apparent size or retained computational dimension.

A second family may later allow k to grow sublinearly with n.

## Baseline path

    Raw full system
        ↓
    ordinary full-system solver
        ↓
    verifier

Measure actual deterministic solver-operation counts under a declared algorithm.

## Oracle-compressed path

    Raw full system
        ↓
    oracle compression certificate
        ↓
    retained core system
        ↓
    same solver family
        ↓
    reconstruction
        ↓
    verifier on the ORIGINAL full problem

The verifier must check the reconstructed full assignment against the original full system.

## Compression certificate

Every example must include:

- original variable list
- retained variable list
- eliminated variable list
- reconstruction expression for every eliminated variable
- original constraints
- retained core constraints
- removed constraints
- dependency edges used for elimination
- exactness flag
- generator provenance

Future learned systems may propose the certificate.

v0.0.32 uses oracle certificates only to establish the achievable lower bound and measurement contract.

## Required metrics

Per example:

- apparent variable count
- retained variable count
- apparent constraint count
- retained core constraint count
- variable compression ratio
- constraint compression ratio
- degree-of-freedom reduction
- raw representation bytes
- compressed representation bytes
- compression-certificate bytes
- baseline solver-operation count
- compressed solver-operation count
- reconstruction-operation count
- verification-operation count
- total deterministic operation vector, kept separated by category
- verified solution equivalence
- full original-problem verification result

Aggregate by (k, n).

## Primary outcome

The experiment should plot / report:

    baseline solver work vs n
    compressed solver work vs n
    retained k vs n

The intended question is:

> when apparent problem size grows while the true independent core stays fixed, does verified execution cost track n or k after valid structural compression?

## Critical fairness rule

The oracle compressor is allowed knowledge unavailable to a real system.

Therefore v0.0.32 may establish only:

- measurement validity
- compression upper bound / lower-cost reference
- potential solver-work reduction
- scaling opportunity

It may NOT establish:

- learned AI can discover the compression
- end-to-end NEUMANN efficiency
- total learned + deterministic superiority

Those belong to later versions.

## KEEP contract

KEEP means the experiment is a valid compression benchmark, not that compression wins.

Required:

1. every generated full system has a unique exact solution
2. every oracle-compressed core has a unique exact solution
3. reconstructed assignments satisfy the original full system
4. baseline and compressed paths produce equivalent verified full assignments
5. compression certificates are complete for every eliminated variable
6. operation counters are deterministic
7. all scale cells are populated
8. no hidden generator dependency is supplied to the baseline solver

Not required:

- representation bytes becoming smaller
- total runtime improving
- any particular solver-work ratio

Negative results must be retained.

## Claim boundary

The first v0.0.32 result will be an oracle structural-compression benchmark.

It does not yet test a learned Structural Compression model.

Its scientific purpose is to define the target that a future learned compressor must approach and to determine whether the controlled problem family actually contains a measurable scaling advantage worth learning.

## Next step after v0.0.32

If the oracle contract shows a real verified scaling opportunity:

### v0.0.33
Learned compression proposal:

    raw problem
      -> tiny model
      -> candidate dependency / elimination certificate
      -> deterministic certificate checker
      -> reduced solver
      -> reconstruction
      -> full verifier

Primary metric:

    fraction of oracle compression recovered
    at fixed verified retention

Only then should NEUMANN begin making empirical claims about learned Structural Compression.


## Implementation freeze before first result

The implementation fixes the remaining unspecified benchmark details before any v0.0.32 quality/scaling result is read.

### Cell cardinality

    examples per (k, n) cell = 32
    total cells = 8
    total examples = 256

Grid:

    (2,4), (2,8), (2,16), (2,32)
    (4,4), (4,8), (4,16), (4,32)

### Generated matrix structure

The independent core uses a dense strictly diagonally dominant integer matrix, guaranteeing nonsingularity.

Every eliminated variable is an exact linear function of the retained core variables.

The full system has block form:

    [ A_core   0 ]
    [   -C     I ]

Therefore the full determinant is the determinant of the core matrix and the full problem has a unique solution whenever the core does.

The baseline solver receives only the full matrix/vector/variable payload. It receives no dependency DAG or compression certificate.

### Declared solver family

Both baseline and compressed paths use the same exact rational Gauss-Jordan implementation.

The solver records separately:

- pivot tests
- row swaps
- scalar divisions
- scalar multiplications
- scalar subtractions

The primary solver-work curve uses:

    arithmetic ops = divisions + multiplications + subtractions

Pivot tests and row swaps remain separately available.

This count is an algorithm-level scalar-operation count for the declared implementation. It is not CPU instructions, FLOPs as measured by hardware, latency, or energy.

### Reconstruction count

Reconstruction is exact rational evaluation of each certificate rule.

It records separately:

- coefficient-value multiplications
- additions

### Verification count

Both paths are verified against the same ORIGINAL full system using exact rational arithmetic.

Verification records:

- equations checked
- nonzero coefficient-value multiplications
- additions

Because the original full problem is identical for both paths, verification work is expected to be identical and is explicitly checked for parity.

### Byte accounting

Canonical compact JSON UTF-8 bytes are reported for:

- raw full solver payload
- compressed core solver payload
- full compression certificate

Ground-truth solutions are excluded from solver-payload byte counts.

The certificate intentionally contains explicit original/core constraint evidence under the v0.0.32 contract. Its byte size is allowed to exceed the raw representation size and no byte-compression win is required for KEEP.

### Scaling diagnostic

For each fixed core dimension k, the benchmark fits an ordinary least-squares slope over:

    log(apparent dimension n)
        vs
    log(mean solver arithmetic operations)

for both baseline and oracle-compressed paths.

This empirical log-log slope is a descriptive scaling diagnostic over the finite pre-registered range. It is not an asymptotic complexity proof.

### Reconstruction and verification do not disappear

The compressed path still pays work that scales with the original problem.

For (k=2):

| n | reconstruction arithmetic ops | original-problem verification ops |
|---:|---:|---:|
| 4 | 6 | 16 |
| 8 | 18 | 36 |
| 16 | 42 | 76 |
| 32 | 90 | 156 |

For (k=4):

| n | reconstruction arithmetic ops | original-problem verification ops |
|---:|---:|---:|
| 4 | 0 | 28 |
| 8 | 28 | 64 |
| 16 | 84 | 136 |
| 32 | 196 | 280 |

Therefore the result is **not** that verified reasoning becomes constant-cost.

The oracle removes the growth of the solver subproblem by compressing it to fixed (k), but reconstruction and independent verification introduce an output / proof obligation that continues to grow with apparent problem size.

This is an important boundary, not a failure of the benchmark.

### Representation bytes: positive and negative result

The solver-facing compressed core becomes much smaller.

At (k=2,n=32):

- raw full solver payload: **2,416.5 bytes**
- compressed core payload: **56.4 bytes**
- raw / compressed payload ratio: **42.87x**

At (k=4,n=32):

- raw full solver payload: **2,450.2 bytes**
- compressed core payload: **107.4 bytes**
- raw / compressed payload ratio: **22.81x**

However, the explicit v0.0.32 certificate is deliberately verbose because it duplicates original/core constraint evidence.

At (k=2,n=32):

- certificate: **7,360.6 bytes**
- certificate / raw payload: **3.05x**
- compressed payload + certificate / raw payload: **3.07x**

At (k=4,n=32):

- certificate: **8,401.3 bytes**
- certificate / raw payload: **3.43x**
- compressed payload + certificate / raw payload: **3.47x**

So v0.0.32 does **not** demonstrate end-to-end byte compression when the full explicit certificate is transmitted/stored alongside the reduced IR.

That negative result is retained.

A future certificate format may reference original constraints by identity/hash and encode only reduction evidence, but changing certificate compactness is a separate experiment and must not be retroactively used to improve v0.0.32.

## Interpretation

The oracle benchmark establishes three narrow facts.

### 1. A real compression opportunity exists in the controlled family

When apparent dimension grows while true independent dimension remains fixed, the declared exact solver's work grows approximately quadratically on the uncompressed full system but remains essentially flat on the retained core.

### 2. Structural Compression moves the bottleneck rather than deleting all work

After compression, solver growth is removed, but reconstruction and verification remain tied to the original problem/output size.

For this benchmark, a more accurate architecture-level picture is:

    expensive full solve
        ↓ Structural Compression
    small core solve
        + reconstruction
        + original-problem verification

The next research question is therefore not merely whether the solver can be made small, but whether certificate checking, reconstruction, and verification can remain sufficiently cheap relative to the avoided solve.

### 3. Evidence representation matters

The reduced solver payload is dramatically smaller, but a naive explicit certificate can overwhelm that gain in bytes.

Structural Compression therefore has at least two distinct optimization targets:

- **computational compression**
- **evidence / certificate compression**

They must be measured separately.

## Decision

**KEEP — oracle Structural Compression benchmark contract is valid.**

The measured solver-work scaling opportunity is large enough to justify proceeding to a learned compression proposal experiment.

This decision does **not** mean learned compression has been demonstrated.

The next gate should ask:

> Can a small learned model recover a useful fraction of the oracle eliminations while every proposed reduction remains subject to deterministic certificate checking and full original-problem verification?

The primary learned-compression metric should be:

    oracle compression recovered
        at fixed verified retention

with false or unverifiable reductions failing closed.
