# v0.0.100 — Matched quotient-point refit + development Q34 screen

## Purpose

v0.0.99 admits an equivalence-quotient point representation before training.
v0.0.100 is the one authorized refit. It is deliberately structured as a
matched representation experiment, not another architecture-tuning loop.

The sealed v0.0.98 holdout is never loaded or evaluated.

## Training data

Use exactly the 48 already-opened v0.0.88 training sources and their already
opened/certified basis labels.

No v0.0.88 final source and no v0.0.98 source/evaluation archive is permitted.

## Matched models

Train two representation families with identical support-only architecture:

- `OLD_CG5`: current v0.0.94 CG5 point features.
- `QUOTIENT`: v0.0.99 quotient point features.

Architecture:

`8 -> 16 ReLU -> 16 ReLU -> 1 score`

433 learned scalars. No row head, primal head, dual head or graph state.

Frozen training seeds: `100001, 100002`.

For both families and both seeds:

- identical initialization seed;
- Adam, lr=0.001, weight_decay=0;
- 12 epochs;
- fixed shuffled order `100091 + epoch`;
- balanced basis BCE with positive weight 15;
- last epoch only;
- no validation/checkpoint selection;
- no early stopping;
- one fit only.

Representation-specific feature-preparation time and fit time are retained and
later amortized over 10,000 queries.

## New opened-development evaluation set

This is **development**, not a final holdout. It is generated only after this
protocol is frozen and may be inspected after the first run.

Base seeds: `100200..100215`.

- first 8: m=64, n=1024;
- next 8: m=128, n=2048;
- alternating condition 1 / 1000;
- same width-factor-16 constructed LP generator lineage.

For every base case, create exactly one mathematically equivalent surface view
using a signed row permutation plus positive column scaling, deterministic seed
`base_seed + 200000`.

This gives four cells of 8 cases:

- `m64_base`
- `m64_surface`
- `m128_base`
- `m128_surface`

The oracle basis is independently certified on every generated view before it
may be used as the nondeployable Oracle reference. Candidate proposal code
receives A,b,c only.

## Routes

- `DIRECT`
- `ORACLE`
- `OLD_CG5_s100001`

## Runtime / timing

Exact retained LP runtime:

- Python 3.12
- NumPy 2.3.5
- SciPy 1.17.0
- scikit-learn 1.9.1
- torch 2.14.0+cpu
- highspy 1.15.1
- OpenBLAS core HASWELL
- numerical/model threads = 1.

For every development case/route:

- 1 warmup;
- 3 retained timed repetitions;
- deterministic serial shuffled order, seed `100991 + repeat`;
- 5 second complete-path budget;
- proposal timer begins before feature construction;
- post timer charges restricted execution, original verification, failures and
  Direct fallback;
- learned discovery additionally charges
  `(representation feature-setup + own fit) / 10000` per query.

## Q34 development metrics

Use the frozen v0.0.96 Q34 definitions and thresholds.

For each candidate route and each cell, and again for all 32 views combined:

- every retained answer must verify;
- positive Oracle and candidate savings;
- utility recovery >=0.80;
- discovery burden <=0.20;
- amortized complete/Direct <1.00.

Both QUOTIENT seeds must pass all four cells and the combined set.

Additionally the QUOTIENT top2m support must be exactly identical between each
base case and its equivalent surface view for all 16 pairs for both seeds.
This is a representation-consistency gate, not a performance proxy.

OLD_CG5 is a matched causal/economic control and does not determine promotion.

## Decision

If both QUOTIENT seeds pass every Q34 cell + combined set and 16/16 paired
support invariance:

`ADMIT_NEW_FRESH_Q34_HOLDOUT_FOR_QUOTIENT`

Freeze the quotient support system. Do not tune on this development result.
A later version may register a **new** fresh holdout with new seeds.

Otherwise:

`STOP_QUOTIENT_REFIT_NO_FRESH_HOLDOUT`

No second fit, no threshold rescue and no reuse of the v0.0.98 holdout.

This version cannot itself advance Q5.
