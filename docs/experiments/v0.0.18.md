# v0.0.18 — Threat Model and Assurance Contract

## Question

Before adding more security mechanisms, what attacker and failure model is NEUMANN actually trying to defend against?

## Method

Convert current security claims into a machine-readable threat model.

Each scenario declares:
- actor
- protected asset
- trust boundary
- prevent assurance
- detect assurance
- contain assurance
- recover assurance
- controls
- evidence identifiers
- residual risk

Strong assurance labels require non-empty evidence.

## Scenarios frozen in v1

1. unapproved plugin activation
2. manifest substitution after approval
3. persisted ledger mutation/reordering
4. valid-prefix ledger rollback
5. post-activation arbitrary plugin code
6. compromised NEUMANN process
7. compromised checkpoint authority

## Main architectural result

The current system has increasingly strong evidence around:
- static discovery
- exact-manifest approval
- use-time managed revocation
- persistent-ledger integrity

But it has no containment boundary after an approved plugin is imported.

Therefore the threat model chooses:

**out_of_process_plugin_isolation**

as the next control priority.

## Why not signatures first?

Signatures solve identity/authenticity questions. They do not prevent signed code from being malicious, compromised, or buggy.

Because approved plugin code currently runs in the same Python process as NEUMANN core, the larger uncontained runtime risk is code execution authority inside the core process.

## Boundary

This version does not add a sandbox.

It freezes the security model so subsequent controls can be judged against explicit threats rather than security aesthetics.
