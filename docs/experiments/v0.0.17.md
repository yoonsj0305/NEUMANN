# v0.0.17 — Durable Hash-Chained Authorization Ledger

## Question

Can NEUMANN preserve plugin authorization state across process restarts while detecting persisted-ledger mutation and making rollback detection explicit?

## Persistent record

Each JSONL authorization event stores:
- ledger version
- sequence number
- action
- plugin ID
- manifest digest
- reason
- previous event hash
- event hash

Event hash is SHA-256 over canonical JSON containing the event body and previous hash.

## Reload verification

On startup the ledger verifies:
- UTF-8 / JSON integrity
- exact record field set
- ledger version
- contiguous sequence
- valid action
- predecessor-hash link
- event hash

Current authorization state is reconstructed only from a verified chain.

## Trusted head / checkpoint

A local hash chain alone cannot distinguish a genuine old ledger from a malicious rollback to a complete older valid prefix.

Therefore the loader optionally accepts a trusted expected head SHA-256 obtained from outside the ledger file.

If the persisted head differs, loading fails closed.

This gives two evidence levels:

### Local chain only
Detects:
- event mutation
- record reordering
- broken links
- malformed/partial records

Does not necessarily detect:
- complete rollback/truncation to an older valid prefix

### Local chain + trusted external head
Also detects:
- complete event truncation
- rollback to older valid ledger state

subject to the trust and availability of that external checkpoint.

## Durability behavior

Append writes are flushed and fsync'd before in-memory state advances.

## Boundary

This is single-writer file persistence.

It does not yet provide:
- multi-process locking
- distributed consensus
- authenticated operator identity
- cryptographic signatures
- immutable/WORM storage
- secure external checkpoint storage
- rollback resistance if an attacker can modify both ledger and trusted checkpoint

The correct claim is tamper-evident relative to the stated trust boundary, not tamper-proof.
