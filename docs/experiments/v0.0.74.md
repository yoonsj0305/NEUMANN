# v0.0.74 — Exact elimination-order learning headroom screen

Status: protocol frozen before timed evaluation. This is **not** a learned
model result, Q4 pass, novelty claim, or representative real-world benchmark.

## Question and scope

Does spending more on elimination-order planning create complete verified
cost savings that a future cheap learned planner could plausibly exploit?
Count independent sets exactly in binary factor graphs. This differs from
the previous maximum-independent-set optimization task. No planted twins,
compression labels, answer oracle, natural-language parsing, or cache is used.

Classical variable elimination and iterative stochastic min-fill are prior
art: [Kask et al., AAAI 2011](https://ojs.aaai.org/index.php/AAAI/article/view/7828).
Learned tree decomposition is directly prior art:
[Khakhulin et al., 2019](https://arxiv.org/abs/1910.08371).
Learned variable ordering is also an established direction (e.g. CSP search,
[Song et al.](https://arxiv.org/abs/1912.10762)); that is not the same as this
sum-product executor. NEUMANN's open question is complete iso-capability cost.
All implementation here is local; no external code/data/weights are imported.
The initial protocol citation incorrectly said 2010 for Kask et al.; the
publisher metadata confirms 2011. This correction changes no experiment rule.

## Frozen interface and comparators

Input: simple undirected adjacency tuples. Output: exact integer count,
elimination permutation, intermediate factor tables, checked proof, timings.

Methods: deterministic min-fill (degree and index tie breaks), deterministic
min-degree (fill and index tie breaks), and best of eight stochastic min-fill
orders. Stochastic candidates use random tie breaks **only among vertices
with minimum fill**. Planning selects by predicted total table assignments,
then induced width, then order. All eight candidate-generation and scoring
costs are charged; only the selected order is executed. This is a bounded
stronger comparator, not the strongest available exact counting engine.

The executor sums products of integer factor tables. A separate checker
reconstructs original edge/unary factors and recomputes each transition
using tuple-valued assignments, not the executor's packed-bit projections.
Every variable occurs once; remaining factors must be scalar; the final
integer must match their product. Tests also use exhaustive counting on
small graphs. This code independence is not a formal proof of checker safety.

## Frozen evaluation

Three synthetic generators: sparse random (expected degree four), bipartite
(expected degree four), and a ring with independent random chords (expected
degree four). Sizes 16, 24, 32; three seeds per cell (740001 onward).
27 graphs, three methods, three rotating timed repeats: 243 timed calls.
One warm-up per graph/method, no timing-based exclusions or retuning.
Each call includes graph validation, planning, execution, proof checking.
10 seconds total cooperative deadline, maximum factor scope 18; failures
stay in the archive and prevent the capability gate. No timeout speed ratios.
No training is run in this screen.

The reference is the **faster measured** min-fill/min-degree total cost on
each graph, deliberately stronger than choosing one baseline after results.
Per-graph repetitions use medians; summary uses geometric mean of ratios.
Advance only if every timed result verifies and agrees, geometric mean of
best-eight/reference total cost is <=0.8, and at least 9/27 graphs improve
by >=20%. This is a screening threshold, not statistical significance.

Also report a diagnostic zero-planning-cost lower bound for the selected
best-eight order: execution+verification/reference. It uses an already
searched order and is **not deployable inference**. If even this bound fails
the same cost thresholds, stop learning on this bounded distribution. If
only the bound passes, freeze a separate learned experiment before training;
do not call the oracle diagnostic a speedup. Future learned results must
charge features, prediction, fallback, training amortization, and model load.

## Degraded mode and risk

Invalid input/order/certificate fails closed. Budget exhaustion returns an
unverified failure, never an approximate count labelled exact. This research
runner does not perform fallback; a later runtime must charge failed planning
and execution before any direct fallback. Factor explosion, Python overhead,
checker domination, selection on this screen, and narrow generator coverage
are explicit risks. Scaling/generalization/reuse remain untested.

## Result

The initial timed run accidentally overlapped the full test suite. Its
unaltered raw archive is `results/v074_contaminated_concurrent_tests.json`;
it is retained but its latency measurements are not admissible. This is an
execution-environment failure, not a timing-based outlier exclusion. Repeat
the exact frozen inputs, methods, and thresholds **after** tests terminate;
do not tune using the contaminated run.

The sequential audit is `results/v074_sequential_audit.json`. All 243 timed
calls independently verified exact counts; all methods/repetitions agreed
on all 27 graphs, with no failures. Best-eight/reference geometric mean
ratio is **1.7567936611**, and 0/27 graphs reached a 20% complete-cost gain.
The zero-planning diagnostic ratio is **0.8823730019**, with 2/27 reaching
20% gains. Both frozen cost screens fail. Decision:
`NO_LEARNED_PLANNER_HEADROOM_ON_FROZEN_DISTRIBUTION`.

Interpretation is restricted to the frozen n=16–32 distribution and the
eight candidate orders. The diagnostic is not a bound on all possible
orders or models. No learned model, real-world deployment, 10× result,
cross-domain reuse, or improved compute-scaling slope was demonstrated.
No training budget will be spent imitating this selected-order policy here.
Timing ratios are latency evidence, not FLOPs, joules, or dollar estimates.
Table/proof entry counts are not peak-process-memory measurements.

The next central task is a genuinely matched model-level comparison that
includes a same-budget direct program/IR predictor, not answer-only
classification. See `docs/research/core_question_gates.md`. This iteration
adds a bounded rejector, not a general high-efficiency model capability.
