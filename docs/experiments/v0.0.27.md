# v0.0.27 — Model-side structural proposal cost contract

## Question

Can NEUMANN measure the learned work used to propose a reusable structural family without confusing that proxy with FLOPs, energy, or LLM efficiency?

v0.0.26 established that a solver-ready representation can amortize repeated interpretation work. v0.0.27 moves one layer upstream and measures the current learned proposer itself.

## Current learned component

The proposer is intentionally small and explicit:

- TF-IDF word + character features
- logistic known-vs-unknown detector
- logistic supported-family classifier
- deterministic threshold selected on a separate validation corpus

This is **not an LLM** and should not be used as evidence for LLM parameter, GPU-memory, token, or energy efficiency.

## Measurement contract

For each final-corpus item, report:

- fitted feature dimensions
- fitted logistic coefficient/intercept scalar count
- TF-IDF IDF-state scalar count, separately from classifier parameters
- sparse active features at the known detector
- sparse active features at the family classifier when routed
- number of learned stages actually executed
- sparse score dot-product term proxy
- model-side wall-clock time as a diagnostic
- proposal coverage / abstention
- proposal false-route rate
- compiler-gated false-route rate
- deterministic solver verification for supported known tasks

The score proxy is:

    active sparse features × fitted coefficient rows actually scored

It is **not** a FLOP count. It omits vectorizer work, nonlinear probability conversion, memory traffic, cache effects, Python overhead, and hardware energy.

## Reuse sub-experiment

For the exact same text repeated N times, compare:

1. learned proposal inference on every use
2. learned proposal once, then exact proposal reuse

This isolates the learned routing layer only.

Downstream deterministic compiler, solver, and verifier obligations are not deleted by this reuse measurement.

## Pre-registered KEEP gate

Using the v0.0.10 final corpus and 8 repeated uses:

1. measurement decision parity with public `predict_kind()` = 1.0
2. known proposal coverage = 1.0
3. known deterministic compiler acceptance = 1.0
4. known end-to-end solver verification coverage = 1.0
5. unsupported final false-route rate after compiler gate = 0.0
6. every measured item has positive score-term proxy
7. repeated proposal prediction is stable
8. repeated score-term reduction factor = 8.0

Not part of the KEEP gate:

- wall-clock speedup
- a particular fitted parameter count
- zero learned proposal false routes before compiler acceptance
- representation byte compression
- any LLM, GPU, memory, or energy claim

## Why compiler rescue matters

A learned proposer is allowed to be imperfect. Its output is advisory.

The architectural claim under test is stronger and narrower:

> a bad learned family proposal must not become solver authority when the deterministic compiler rejects the raw input.

Therefore proposal-layer false routes are reported, not hidden. The final compiler-gated false-route rate is the authority boundary.

## Boundary

This experiment provides an auditable cost vocabulary for the current small proposer. It does not yet compare NEUMANN against a direct learned solver and does not establish that structural proposal is cheaper than an LLM reasoning path.

The next scientifically meaningful step after this contract is to place a real small language model or another learned solver under the same measurement vocabulary rather than extrapolating from TF-IDF/logistic regression.
