# v0.0.35 — Compression Economics Audit

Status: pre-registered research specification

## Why this experiment exists

v0.0.34 established a central negative result:

- the frozen learned scorer best reproduced generator dependency-reference labels,
- but target-leaf and Markowitz-style heuristics produced larger downstream solver savings,
- therefore reference-label accuracy is not the objective of Structural Compression.

However, v0.0.34 still reported the final reduced-system solver work separately from the cost of certifying each proposed reduction.

The current fail-closed checker calls `materialize_reduction` after each tentatively accepted candidate. A successful materialization performs:

1. retained-system construction,
2. exact Gauss-Jordan solve,
3. affine reconstruction,
4. full original-problem verification.

The final accepted set is then materialized once more.

Therefore a system can report a much smaller *final solver* while having already spent more arithmetic work validating intermediate reductions than it saved.

v0.0.35 audits that possibility before adding a new utility model.

## Central question

> Does the current certified Structural Compression path save arithmetic work once a conservative lower bound on successful checker materializations is included?

This is a prerequisite question for later Value-of-Reduction learning.

## Frozen inputs

v0.0.35 does not train a new model and does not tune on new final data.

It reuses:

- the immutable v0.0.33 learned scorer checkpoint,
- the v0.0.34 calibration split,
- the v0.0.34 final split,
- the v0.0.34 threshold grid,
- the v0.0.34 threshold-selection rule,
- the exact same candidate universe,
- the exact same deterministic scorer formulas,
- the exact same final method ordering and checker authority.

No v0.0.35 metric may change a v0.0.34 threshold.

## Methods

Audit every v0.0.34 method:

1. learned_mlp
2. deterministic_random
3. target_leaf
4. row_sparsity
5. sparsity_incidence
6. dependency_contrast
7. markowitz
8. structural_combo

## Baseline arithmetic work

For each final example, define the no-compression baseline as:

```
baseline_total_arithmetic
    = full_system_solver_arithmetic
    + full_system_verification_arithmetic
```

This is an unweighted count of arithmetic-operation events already exposed by the deterministic instrumentation.

It is not FLOPs, latency, energy, or hardware cost.

## Successful-path certification lower bound

Mirror the existing checker exactly.

For every proposal that passes row/target conflict checks, attempt the same tentative `materialize_reduction`.

For every *successful* tentative materialization, accumulate:

- solver arithmetic ops,
- reconstruction arithmetic ops,
- verification arithmetic ops.

After proposal processing, materialize the final accepted set exactly as the current checker does and include that final successful materialization in the accumulated totals.

Define:

```
successful_path_lb_solver
successful_path_lb_reconstruction
successful_path_lb_verification

successful_path_lb_total
    = successful_path_lb_solver
    + successful_path_lb_reconstruction
    + successful_path_lb_verification
```

This is deliberately an optimistic lower bound on the current compression path.

It excludes:

- learned scorer arithmetic,
- deterministic heuristic arithmetic,
- candidate enumeration,
- Python/runtime overhead,
- certificate serialization,
- rejected materialization attempts whose internal work is not currently surfaced,
- memory traffic,
- wall-clock effects.

If this lower bound already exceeds the baseline, the current compression economics fail decisively for that method/example.

## Additional checker diagnostics

Report:

- proposals considered,
- accepted candidates,
- conflict rejections,
- materialization rejections,
- successful tentative materializations,
- final materialization count,
- total materialization attempts,
- accepted-path re-solve multiplicity.

Because the existing checker rematerializes after every accepted candidate and again at the end, the expected successful materialization count is approximately:

```
accepted_candidates + 1
```

for examples with any accepted compression.

## Primary metrics

For every method:

- verified retention,
- unsafe accepted reduction count,
- mean final solver ops,
- mean final solver savings vs baseline solver,
- mean baseline total arithmetic,
- mean successful-path lower-bound solver arithmetic,
- mean successful-path lower-bound reconstruction arithmetic,
- mean successful-path lower-bound verification arithmetic,
- mean successful-path lower-bound total arithmetic,
- mean lower-bound / baseline arithmetic ratio,
- median lower-bound / baseline arithmetic ratio,
- p90 lower-bound / baseline arithmetic ratio,
- fraction of examples with ratio < 1,
- fraction of examples with ratio >= 1,
- mean successful materialization count,
- mean materialization-rejection count.

## Required consistency checks

The audit implementation must also prove on every final example that its mirrored checker produces exactly the same:

- accepted candidate keys,
- rejected candidate keys,
- final retained system,
- final full answer,
- final solver arithmetic count,
- final verification result

as the frozen v0.0.34 checker.

If mirrored behavior differs, the experiment is invalid.

## Decision rule

### Decisive negative

If the strongest v0.0.34 methods have:

```
mean successful_path_lb_total / baseline_total_arithmetic >= 1
```

then the current per-candidate rematerialization checker is frozen as a correctness prototype, not an economically viable compression runtime.

The next milestone must prioritize a cheaper certification architecture before learned Value-of-Reduction optimization.

### Inconclusive-but-allowed

If the lower-bound ratio is < 1, this does **not** establish end-to-end compute savings because omitted costs remain.

It only permits the next milestone to instrument the omitted costs and/or proceed to a utility-learning experiment under explicit economics accounting.

## Architecture consequence if the audit fails

The preferred redesign target is not weaker verification.

It is:

```
score / rank candidates
    -> cheap local structural admission
    -> accumulate a candidate batch
    -> bounded final exact materialization
    -> reconstruction
    -> original-problem verification
    -> fail closed / fallback if final batch is invalid
```

The design goal is to remove repeated full reduced-system solves from the inner proposal loop.

Candidate future mechanisms include:

- incremental rank / factorization certificates,
- batch validation,
- bounded rollback,
- divide-and-conquer subset recovery,
- cached elimination state,
- solver-state reuse.

These are future work and are not part of the v0.0.35 result.

## KEEP contract

KEEP means the audit is methodologically valid, not that compression is economical.

Required:

1. v0.0.34 scorer and thresholds remain frozen,
2. v0.0.34 final examples remain unchanged,
3. mirrored checker decisions exactly match the existing checker,
4. successful-path lower-bound accounting includes every successful tentative materialization and the final materialization,
5. rejected hidden work is not silently counted as zero-cost evidence of efficiency,
6. all omitted costs are listed explicitly,
7. verified retention remains 1.0 for every released-safe method,
8. unsafe accepted reductions remain 0,
9. no total-FLOP, energy, or latency claim is made from arithmetic-event counts.

## Claim boundary

A negative result can support:

> under the frozen v0.0.34 affine-linear benchmark, the current fail-closed checker spends at least X times the no-compression baseline arithmetic work on successful materializations alone, despite reducing the final retained-system solver work.

A lower-than-baseline result can support only:

> the successful-materialization arithmetic lower bound does not by itself rule out end-to-end savings.

It cannot establish:

- total compute savings,
- latency savings,
- energy savings,
- hardware efficiency,
- domain-general compression economics,
- optimal certification architecture.
