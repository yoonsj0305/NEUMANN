# v0.0.35 — Compression Utility / Value-of-Reduction Oracle

Status: pre-registered research specification

## Motivation

v0.0.34 produced the central negative result:

> better reproduction of generator reference rules does not imply better verified Structural Compression.

The frozen learned scorer achieved the strongest reference-rule F1, while simpler deterministic heuristics produced lower downstream solver work.

Therefore v0.0.35 changes the optimization target.

The experiment does **not** train a new learned utility model.

It first asks whether downstream computational utility itself provides a better target than generator-reference imitation.

## Core decomposition

NEUMANN now separates three primitives:

1. **Validity** — is a proposed reduction safe and reconstructible?
2. **Utility** — how much verified execution work does the reduction remove?
3. **Stopping** — when does another accepted reduction cease to improve the declared execution objective?

Authority remains unchanged:

    scorer / utility estimator
        ↓ advisory only
    deterministic reduction checker
        ↓ authority
    exact retained solve
        ↓
    reconstruction
        ↓
    verify ORIGINAL full problem

## Primary research question

> Does selecting certified reductions by measured Value-of-Reduction reduce downstream solver work more than selecting them by reference-label similarity or fixed local heuristics?

## Utility definition

For a valid tentative reduction set R, define:

    C_solver(R)
        = exact Gauss-Jordan arithmetic-operation count
          of the retained system

For adding candidate c to current accepted set R:

    VoR(c | R)
        = C_solver(R) - C_solver(R ∪ {c})

Positive VoR means the candidate reduces the declared solver-work proxy.

This is a narrow operational utility definition.

It is **not** total compute, energy, latency, or dollar cost.

## Methods

### A. Dynamic greedy marginal-utility oracle

Start from R = empty.

At each step:

1. enumerate candidates not conflicting with already accepted row/target identities,
2. materialize each tentative R ∪ {c},
3. reject invalid tentative reductions,
4. measure VoR(c | R),
5. choose the candidate with the largest positive VoR,
6. tie-break deterministically by row index then target index,
7. stop if no valid candidate has VoR > 0.

This is an expensive teacher/oracle.

It is **not** a deployable inference policy and no end-to-end efficiency claim may be made from it.

It is called an oracle only with respect to the declared greedy marginal-utility rule.

It is not a globally optimal compression oracle.

### B. Static isolated-utility ranking

For every candidate c, measure:

    isolated_VoR(c)
        = C_solver(empty) - C_solver({c})

Rank candidates by descending isolated_VoR.

Only candidates with isolated_VoR > 0 are proposed.

The unchanged deterministic checker processes them in that order.

This tests whether a cheap, state-independent utility target is sufficient, or whether interaction terms materially matter.

### C. v0.0.34 learned-reference scorer

Reuse the immutable v0.0.33 checkpoint used by v0.0.34.

No retraining and no architecture change.

Its threshold is calibrated on the v0.0.35 calibration split to maximize mean verified solver savings, not reference-rule F1.

### D. Deterministic structural baselines

Reuse the v0.0.34 deterministic scorers:

- target-leaf
- row-sparsity
- sparsity + incidence
- dependency contrast
- Markowitz
- fixed structural combo

Thresholds are calibrated on the v0.0.35 calibration split to maximize mean verified solver savings.

The deterministic random scorer remains a chance control.

## Utility-aware threshold calibration

Threshold grid:

    tau in {
        0.05, 0.10, 0.15, 0.20, 0.25,
        0.30, 0.35, 0.40, 0.45, 0.50,
        0.55, 0.60, 0.65, 0.70, 0.75,
        0.80, 0.85, 0.90, 0.95
    }

For each scorer and threshold on the calibration split:

1. score candidates,
2. keep candidates with score >= tau,
3. run the unchanged deterministic checker,
4. require original-problem verification,
5. measure baseline solver ops minus compressed solver ops.

Selection objective:

    maximize mean verified solver savings

Tie-breaks, in order:

1. lower mean compressed solver ops,
2. fewer mean proposed candidates,
3. higher threshold.

Final examples are not used for threshold selection.

## New data split

Use the same leakage-hardened affine-linear generator family as v0.0.33–v0.0.34.

Scale grid:

    k in {2, 4}
    n in {4, 8, 16, 32}
    n >= k

Per cell:

    calibration = 24
    final       = 32

Seeds are new for v0.0.35.

Every v0.0.35 calibration/final full-system signature must be disjoint from:

- v0.0.33 training
- v0.0.33 validation
- v0.0.33 final
- v0.0.34 calibration
- v0.0.34 final

and calibration/final must be mutually disjoint.

## Primary metrics

For every method report:

- verified retention
- unsafe accepted reduction count
- mean accepted eliminations
- mean compressed solver arithmetic ops
- mean solver savings vs full baseline
- mean retained dimension
- mean proposal count where applicable
- fail-closed rejection count where applicable

For utility oracles additionally report:

- utility trial materializations
- cumulative trial solver arithmetic ops
- mean positive marginal gain selected
- stopping count

These oracle-search costs must remain separate from final retained-system solver work.

Do not combine unlike work units into a synthetic total-compute score.

## Interaction diagnostic

Define:

    interaction_gain
        = dynamic_greedy_solver_savings
          - static_isolated_solver_savings

Report the aggregate and per-cell value.

Positive interaction_gain indicates that state-dependent marginal utility matters beyond isolated candidate value.

## Main comparisons

Primary:

1. dynamic greedy marginal-utility oracle vs target-leaf
2. dynamic greedy marginal-utility oracle vs Markowitz
3. static isolated utility vs dynamic greedy utility
4. utility-calibrated frozen learned-reference scorer vs its v0.0.34-style reference objective result, descriptively
5. best utility-calibrated pre-registered heuristic vs learned-reference scorer

No new learned utility model is introduced in v0.0.35.

## KEEP contract

KEEP means the experiment is methodologically valid, not that utility wins.

Required:

1. v0.0.35 data are disjoint from all v0.0.33/v0.0.34 data,
2. calibration and final are disjoint,
3. final data do not select thresholds,
4. all learned state is frozen before v0.0.35 final evaluation,
5. utility is measured only from deterministic exact retained solves,
6. deterministic checker remains authoritative,
7. every final method retains 100% original-problem verification,
8. unsafe accepted reduction count is zero,
9. dynamic greedy tie-breaking is deterministic,
10. all scale cells are complete,
11. no method receives generator k or n-k at final inference,
12. oracle search cost is reported separately from downstream solver work.

Not required:

- dynamic utility beats every heuristic,
- static utility beats target-leaf,
- learned-reference scoring improves,
- total-compute superiority,
- globally minimal retained structure.

## Interpretation rules

If dynamic utility materially beats static isolated utility:

    next learned model should be state-aware.

If static utility is close to dynamic utility and beats structural heuristics:

    first learn the static utility target with the smallest adequate model.

If target-leaf / Markowitz remain competitive with the utility oracle:

    preserve them as first-class architecture components
    and do not add learned complexity without a measured benefit.

If utility targeting improves solver work but oracle-search cost is large:

    treat v0.0.35 as teacher-signal validation only.

## Claim boundary

A positive result would support only:

> on this generated exact affine-linear family, selecting certified reductions using downstream solver-work utility can improve retained-system execution cost relative to reference-rule imitation and/or fixed local heuristics.

It would not establish:

- globally optimal compression,
- natural-language Structural Compression,
- domain-general utility learning,
- end-to-end total-compute superiority,
- energy or latency superiority,
- asymptotic complexity improvement.
