# v0.0.21 — Persistent Worker Lifecycle Experiment

## Question

Can NEUMANN remove the fresh-process lifecycle bottleneck without giving up the v0.0.19 process boundary and v0.0.16 revocation semantics?

## Architecture

Fresh-process v0.0.19:

`compile child → exit → solve child → exit → verify child → exit`

Persistent-worker v0.0.21 experiment:

`start child once → import/activate once → compile → solve → verify → reuse`

Transport remains JSON over stdin/stdout, now line-delimited with request IDs.

## Required invariants

- plugin remains outside parent Python process
- exact manifest approval required before worker start
- authorization rechecked before every request
- revoke sends **zero** subsequent plugin requests
- revoke terminates the existing worker
- timeout kills worker and fails closed
- crash invalidates worker and fails closed
- next approved request may start a clean replacement worker
- request/response IDs must match

## Pre-registered keep gate

Before CI result is observed, keep the persistent-worker direction only if:

1. warm persistent full-pipeline median <= 25% of fresh-process median
2. revoked execution is not verified
3. post-revocation plugin requests = 0
4. worker is terminated after revocation

This is an experiment gate, not a universal production SLO.

## Important semantic change

A persistent worker retains Python process state between requests.

This means plugin globals, caches, allocator state, and accidental mutable state may persist.

That can be useful for performance, but it is also a new source of nondeterminism and cross-request contamination. Future work must decide what state persistence is allowed and when workers are recycled.

## Security boundary

Persistent workers do not improve the host security boundary.

They still run as the same OS user unless an independent sandbox restricts capabilities.

Threat Model v2 therefore continues to set:

`os_level_capability_sandbox`

as the next security control priority.

## Interpretation

The pre-registered performance gate was exceeded by a large margin in this lightweight probe.

The ~2394× ratio must **not** be generalized to representative reasoning workloads. The benchmark family intentionally performs almost no useful computation, so it magnifies lifecycle cost.

The robust engineering result is narrower:

> Once startup/import cost is amortized, the same out-of-process plugin boundary can serve repeated lightweight compile/solve/verify requests with approximately millisecond-scale warm pipeline latency in this CI environment while preserving the tested revocation invariants.

The cold path remains dominated by worker startup (~741 ms). Therefore a production lifecycle policy must consider:
- when to prewarm workers
- how long to retain idle workers
- when to recycle stateful workers
- how many workers per plugin/family to permit
- how crash recovery affects outstanding requests

## Decision

**KEEP persistent-worker direction as the preferred performance path.**

Security remains a separate track:

`os_level_capability_sandbox`

Persistent state reuse is not itself a security improvement.
