# v0.0.63 — SEMI scenario interface and original-model verifier

Status: **nonblind enabling audit**, not a compression performance test.
The [SIPLIB SEMI page](https://www2.isye.gatech.edu/~sahmed/siplib/semi/semi.html)
describes semiconductor tool-purchase planning instances with mixed-integer
first-stage and continuous second-stage variables. Its public `semi.ZIP`
contains a core MPS, a stage-boundary file and three scenario files. The
original ZIP is used locally and is **not redistributed** in this repository.
Its SHA-256 is
`f43f9cb87c2ce9f133d05c46c9dd631d401aa440e2848312ad8e61bd4f89bff3`.

## What is compiled

The observed `semi.time` interface places 612 integer variables and two
rows in stage one. The common second stage contains 9,802 continuous
variables and 5,842 rows. The three `semi*.stoch` files specify 2, 3 and 4
ROOT scenarios respectively, with probability mass summing to one. Their
header says `SCENARIOS DISCRETE ADD`; the only stochastic entries observed
are 13 RHS deltas per nonbase scenario. The compiler treats them as
**additive** changes to core RHS. That interpretation follows the file's
explicit `ADD` marker; it is a bounded parser for this dataset rather than
a general SMPS parser. Unsupported trees, entries or changed source bytes
fail closed. The original SMPS and the expanded form have separate
variable views in the original-model verifier.

The deterministic equivalent retains one shared first-stage block and one
recourse block per scenario. Its first-stage cost is unchanged; each
second-stage cost is weighted by the declared scenario probability. The
row bounds receive the scenario's RHS deltas. Dimensions match the
source page for all three instances:

| Instance | Scenarios | Variables | Integer | Rows | Nonzeros in compiled form |
| --- | ---: | ---: | ---: | ---: | ---: |
| SEMI2 | 2 | 20,216 | 612 | 11,686 | 80,280 |
| SEMI3 | 3 | 30,018 | 612 | 17,528 | 120,114 |
| SEMI4 | 4 | 39,820 | 612 | 23,370 | 159,948 |

All three expanded models are accepted by HiGHS 1.15.1. The independent
verifier re-evaluates the original core's stage-one and scenario-specific
rows, first-stage integrality and expected objective from the ZIP, rather
than accepting the expanded solver model's status as sufficient.

## Exploratory sanity run and limits

After fixing a verifier bookkeeping bug found during an initial exploratory
20-second solve, a fresh SEMI2 sanity run with a **3-second solver limit**
returned an incumbent. Its independently computed objective was
`6276.363569110424`, within `9.1e-13` of HiGHS's objective; maximum
normalized original-model primal error was `5.1e-12` and integrality error
zero. Deliberately perturbing an integer column by 0.5 and a recourse
column by 1,000 caused the verifier to reject both answers. The complete
model-transfer-plus-solve elapsed time was 3.346 seconds, but the solver
hit its time limit with relative gap `0.79069`. This is **not** a fixed
capability result, an optimal solution or a full-path benchmark. The earlier
exploratory 20-second run had objective about 1711 and gap about 0.204,
but the verifier bug makes that trace unsuitable as acceptance evidence;
it is retained here solely as transparent calibration history.

`benchmark_v063.py` and `results/v063_semi_ingestion_audit.json` record the
reproducible validation. Run with optional audit dependency `highspy==1.15.1`:

```sh
python benchmark_v063.py --archive /path/to/semi.ZIP \
  --output docs/experiments/results/v063_semi_ingestion_audit.json
```

## Decision and next direct test

**INTERFACE_READY, CAPABILITY_NOT_TESTED.** The new workload gives a
problem-specified two-stage structure and an independent answer checker.
It does not yet establish a compression mechanism. The next direct test
must identify one exact scenario/recourse reduction with a checkable
sufficiency certificate, compare its whole path to native HiGHS presolve
and deterministic-equivalent MIP, and freeze a reachable objective-plus-gap
capability before timing. Existing decomposition algorithms (for example
classical Benders) are baselines or reusable components, not a NEUMANN
novelty claim. If the candidate cannot produce a certifiable feasible
original solution or the baseline cannot meet a shared gate within the
budget, report an unreached/invalid gate and do not claim a speed ratio.

The SEMI2/3/4 instances share one core and are not independent holdouts.
If a mechanism is selected using SEMI2, SEMI3/4 can test scenario-count
behavior but cannot establish cross-family generalization. A distinct
source family is required for that claim.
