# v0.0.97 — Q34 support-system architecture tournament preregistration

## Purpose

v0.0.96 showed that the frozen 2m representation already contains the complete
reference basis on 46/48 opened cases for both seeds, while exact-m generation
does not improve when early compression is removed. v0.0.97 therefore stops
optimizing an exact basis head and compares complete support systems.

This is the first Q34 architecture tournament. It uses only already-opened
development inputs and frozen checkpoints. It may admit a fresh Q34 holdout,
but it cannot itself close Q3/Q4 or advance to Q5.

## Frozen development set

Use exactly the first 16 v0.0.88 opened training sources, in retained order.
No final/holdout source may be loaded. Existing v0.0.88 point16/full16
checkpoints for seeds 87001 and 87002 are frozen. No fitting, checkpoint
selection or hyperparameter sweep is permitted.

## Common observable preparation

A/B/C/D use the same v0.0.94 CG5 observable features. Hidden basis labels are
unavailable to every proposal. They are used only by the nondeployable oracle
reference after all candidate contracts are frozen.

## Routes

- `DIRECT`: cold native full-LP solve + original certificate.
- `ORACLE`: exact retained reference basis supplied for free to the restricted
  native executor + original certificate. It is a nondeployable post-discovery
  lower-bound reference, not a candidate.
- `A_DETERMINISTIC`: CG5 centred residual ranks columns; top2m support;
  restricted native solve; original verification; charged cold fallback.
- `B_POINT_sSEED`: frozen point16 head ranks CG5 columns; top2m support;
  restricted solve; original verification; charged fallback.
- `C_FULL_sSEED`: frozen full16 graph sees all n columns and emits top2m
  support; no point-head work is charged to this route; restricted solve,
  original verification and fallback are identical.
- `D_ADAPTIVE_sSEED`: frozen point16 ranking is computed once, then supports
  are attempted in the fixed order m -> 2m -> 4m -> full Direct. Each failed
  restricted solve and original verification is charged. No label or hidden
  oracle may choose expansion.

The adaptive route is a different end-to-end computation contract, not another
fixed graph re-rank.

## Timing and authority

- dedicated one-shot job; no concurrent pytest/benchmark process on the runner;
- Python/runtime package versions must match the retained LP runtime;
- OpenBLAS core HASWELL and all numerical/model thread counts = 1;
- one warmup + three retained timed observations per case/route;
- serial shuffled schedule, fixed order seed 97991 + repeat;
- 5 second complete-path budget per route/case;
- proposal timer starts before CG5 features and includes tensor conversion,
  model inference and support construction;
- post timer includes every restricted/full native attempt and every
  original-LP verification;
- Direct and Oracle pay their full executor/verifier cost;
- setup/import/source loading is outside warm per-query timing and reported
  separately; no energy/FLOP/peak-memory claim in v0.0.97.

All accepted answers require the same original-LP certificate.

## Q34 metrics

For each case use medians across the three retained timed repetitions.

Let:

- `C_D` = Direct complete median,
- `C_O` = Oracle post median,
- `C_disc` = candidate proposal median plus the frozen learned-investment amortization described below,
- `C_post` = candidate post-proposal median, including failed restricted
  attempts and full fallback.

Aggregate before ratios:

`S_oracle = sum(C_D - C_O)`

`S_candidate = sum(C_D - C_post)`

`utility_recovery = S_candidate / S_oracle`

`discovery_burden = sum(C_disc) / S_candidate`

`complete_ratio = sum(C_disc + C_post) / sum(C_D)`

For learned B/C/D routes, `C_disc` also charges `(v088 training_setup_ms + own checkpoint fit_ms) / 10000` on every query. B and D charge their corresponding `point16` checkpoint; C charges its corresponding `full16` checkpoint. This is intentionally conservative shared-setup attribution. A/Direct/Oracle have zero learned investment. Checkpoint restoration and source decoding are reported as setup costs but are not used to rescue or fail this development gate; any future deployment/lifetime claim must close those costs separately.

A route is Q34-development-pass only when:

1. every retained timed observation returns an original-LP verified answer;
2. `S_oracle > 0` and `S_candidate > 0`;
3. utility recovery >= 0.80;
4. discovery burden <= 0.20;
5. complete ratio < 1.00.

For B/C/D, **both frozen seeds must pass** for the family to pass. A passes on
its single deterministic route.

The 0.80/0.20 thresholds are inherited unchanged from the frozen Q34 joint gate.

## Development decision

- If at least one family passes, decision
  `ADMIT_FRESH_Q34_HOLDOUT`. Do not tune on these 16 cases. Freeze the Pareto
  survivor(s) and immediately test them on a separately generated/registered
  fresh Q34 set.
- If no family passes, decision
  `NO_FROZEN_FAMILY_Q34_CANDIDATE`. Do not train automatically. Inspect the
  Pareto/residual ledger first. Only a clearly identified residual gap may
  authorize a new fit.
- Pareto-dominated routes are not carried forward.

This development tournament is not a paper-level or global Q34 pass.
