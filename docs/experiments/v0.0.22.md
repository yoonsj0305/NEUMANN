# v0.0.22 — Worker State Hygiene + Recycling Contract

## Question

Can NEUMANN retain persistent-worker performance while making hidden in-process plugin state explicit, auditable, and resettable?

## Problem introduced by v0.0.21

A persistent worker can retain:
- module globals
- caches
- RNG state
- allocator/runtime state
- open handles
- accidental mutable history

That state may improve performance, but semantic correctness must not silently depend on it.

## Contract

Each worker lifecycle now has an explicit `generation_id`.

Every persistent RPC response is bound to that generation. A mismatched generation is a protocol error and the worker is discarded.

`WorkerStatePolicy` supports:

`max_requests_per_worker`

where the count includes plugin operations (compile/solve/verify) but not initialization/shutdown.

When the limit is reached, the next operation starts a new generation.

Manual `recycle(reason)` is also available and records:
- reason
- old generation ID
- old worker PID
- plugin-operation count in that generation

## Semantic rule

> A family may use retained state as an optimization, but the correctness of a request must be reconstructible from the explicit RPC request plus approved plugin artifact. Hidden worker state is not semantic authority.

Strong probe:

Set `max_requests_per_worker=1`, forcing compile, solve, and verify for one problem to occur in three separate worker generations.

If the family remains correct, the explicit Representation / answer / verification payloads carry the necessary semantics.

## Poisoned-state probe

The test plugin intentionally exposes a hidden global `POISONED` flag.

Expected behavior:
1. poison worker state
2. observe poison in same generation
3. recycle worker
4. observe clean state in new generation

This demonstrates that process recycle resets Python in-memory plugin state for the test fixture.

## Boundary

Worker recycle does **not** reset external side effects such as:
- filesystem writes
- network or remote-service state
- child descendants that escape lifecycle control
- external databases
- other host resources

Therefore state hygiene is narrower than OS sandboxing or transactional side-effect rollback.

## Keep gate

Keep the v0.0.22 contract only if:
- poisoned state is visible inside the same generation
- poisoned state is absent after recycle
- generation ID changes after recycle
- a normal solve remains verified when compile/solve/verify are forced into three separate generations
- parent process still does not import plugin code

## Main finding

> **Hidden Python worker state can influence later requests inside one generation, and process recycling demonstrably removes that in-memory state for the test fixture. At the same time, the explicit RPC/Representation contract is sufficient for the tested family to remain correct even when compile, solve, and verify run in separate generations.**

## Performance consequence

State hygiene has a measurable lifecycle cost.

In this CI run:
- warm reuse: ~1 ms
- one recycle + cold restart: ~847 ms
- forced restart before every operation: ~2.58 s for one pipeline

Therefore `max_requests_per_worker` is not merely a correctness knob. It is a performance/correctness trade-off parameter.

No universal default recycle interval is claimed in v0.0.22. Representative workloads and state-risk classes are needed before selecting one.

## Decision

**KEEP generation IDs, explicit recycle events, and configurable request-count recycling.**

Do not make hidden worker state semantic authority.

## Next research-engineering question

The remaining lifecycle problem is policy selection:

> **How should NEUMANN decide when a worker is safe to reuse, must be recycled, or should never be persistent at all?**

A candidate next milestone is a **Worker State Declaration / Lifecycle Class** that distinguishes:
- stateless semantic families
- cache-only retained state
- explicitly stateful families
- non-persistent-only families

and maps those declarations to enforceable lifecycle policy rather than relying on one global request-count threshold.
