# v0.0.13 — Static Plugin Manifest + Explicit Activation

## Question

Can NEUMANN discover and inspect a plugin's declared identity and capabilities before importing or executing plugin code?

## Principle

Discovery != Trust != Execution.

A plugin appearing in a catalog must not automatically grant code execution.

## Manifest v1

Manifest version:

neumann.plugin.manifest.v1

Required metadata:
- plugin_id
- plugin_version
- family_id
- kind
- family contract version
- entry point
- declared capabilities

The manifest also exposes a canonical SHA-256 digest for audit identity.

Important:
A digest is not a signature and does not establish publisher authenticity.

## Static catalog

PluginCatalog stores validated manifests only.

Catalog registration:
- validates metadata
- detects duplicate plugin IDs
- detects duplicate family IDs
- detects duplicate kind IDs
- does not resolve or load the entry point

## Explicit activation

PluginActivator performs a later, explicit step:

manifest
→ activation policy
→ resolver(entry_point)
→ factory()
→ FamilyAdapter
→ manifest/adapter identity check

The default metadata policy rejects plugins declaring:
- network
- filesystem.write
- subprocess

before resolver code is called.

This is only pre-import policy. It is not a sandbox after import.

## Why this matters

NEUMANN now has three distinct boundaries:

1. Discover metadata
2. Decide whether activation is allowed
3. Execute a family adapter

Keeping these separate is necessary if the ecosystem later grows beyond trusted in-repo code.
