# v0.0.33 — Learned Compression Proposal

Status: pre-registered research specification

## Purpose

v0.0.32 established an oracle Structural Compression opportunity on a controlled linear family.

v0.0.33 asks the next narrower question:

> Can a small learned model identify useful eliminations from the full problem, while deterministic checking retains authority over every reduction?

The primary metric is:

    oracle compression recovered
        at fixed verified retention

This version does **not** ask the learned model to infer the minimum retained dimension itself.

To isolate compression-discovery quality from stopping/minimality quality, the proposal budget is fixed to the oracle elimination count:

    proposal budget = n - k

This is an oracle-cardinality control and is a major limitation of v0.0.33.

A later experiment must remove it.

## Leakage hardening relative to v0.0.32

The v0.0.32 generator used obvious internal names and ordered block structure.

Those are unacceptable learned-model cues.

v0.0.33 therefore uses a new generated family with:

- generic observed variable names only
- randomized variable order
- randomized equation order
- affine dependency rules with nonzero offsets allowed
- dependency chains that may reference earlier derived variables
- no observed c*/d* naming convention
- no fixed "core rows first, dependency rows last" order

The oracle dependency DAG remains evaluation metadata and is never passed to the learned proposer.

## Problem family

An example is created from:

1. a nonsingular k-variable core system,
2. n-k derived variables,
3. exact affine dependency rules.

A derived variable may be defined as:

    z = c + a*x + b*y + ...

The corresponding equation is inserted into the full square system.

After construction, rows and columns are independently permuted.

The full system remains exactly solvable.

## Candidate universe

The learned model does not receive oracle candidate identities.

A deterministic syntax-neutral enumerator creates all algebraically possible row-target candidates satisfying:

- target coefficient is +1 or -1
- the row has at least two nonzero coefficients

For each candidate, the row can be rearranged into an affine reconstruction rule.

This enumerator does not decide which candidates should be used for compression.

The learned model scores every candidate.

## Learned proposer

Initial model:

- scikit-learn MLPClassifier
- one hidden layer
- 16 hidden units
- tanh activation
- deterministic random_state
- fixed feature contract
- no variable-name feature
- no row-index feature
- no column-index feature
- no oracle k feature

Candidate features are local/global matrix statistics only, including:

- apparent dimension
- row density
- row coefficient magnitude statistics
- RHS magnitude
- target-column incidence
- target-column coefficient mass
- candidate dependency count
- dependency-column incidence statistics
- relative target/dependency incidence

The feature extractor is fixed before final results.

## Training / validation / final splits

Pre-register the same structural scale grid:

    k in {2, 4}
    n in {4, 8, 16, 32}
    valid cells require n >= k

Per cell:

    training examples   = 96
    validation examples = 24
    final examples      = 32

The three splits use separate deterministic seeds.

Exact full-system signatures must be disjoint across splits.

The n=k cell remains as a no-compression safety control.

## Proposal budget

For each example:

    top-B candidates by learned score
    B = n - k

No probability threshold is tuned on final data.

This deliberately supplies oracle cardinality while withholding oracle identities.

## Deterministic reduction checker

The learned model never directly creates execution authority.

Candidates are processed in learned-score order.

A candidate is accepted only if the tentative reduction remains checkable.

The checker requires:

- unique removed row
- unique eliminated target
- exact algebraic agreement between candidate rule and original row
- acyclic reconstruction dependency graph
- square retained subsystem
- exact retained subsystem solvability
- exact reconstruction
- verification against the ORIGINAL full problem

If a candidate fails, it is rejected and compression proceeds with the safe accepted subset.

Therefore:

> Learned Compression Proposal != Valid Reduction

## Metrics

Per example report:

- oracle elimination count
- proposal budget
- exact-oracle candidate hits in top-B
- accepted eliminations
- rejected proposals
- accepted exact-oracle eliminations
- accepted non-oracle but valid eliminations
- elimination-count recovery:
  
      accepted eliminations / oracle eliminations

- exact-oracle-rule recovery
- baseline solver arithmetic operations
- oracle solver arithmetic operations
- learned-compressed solver arithmetic operations
- oracle solver savings
- learned solver savings
- fraction of oracle solver savings recovered
- reconstruction operations
- original-problem verification operations
- final full-problem verified result

## Safety / quality metrics

Aggregate:

- final verified retention
- unsafe accepted reduction count
- examples with any accepted compression
- mean elimination-count recovery
- mean exact-oracle-rule recovery
- mean oracle-solver-savings recovery
- fail-closed rejection count

A false proposal that is rejected is not a correctness failure.

An invalid reduction that reaches execution would be a correctness failure.

The target is:

    unsafe accepted reduction count = 0

## Learned cost contract

Report:

- input feature dimension
- hidden width
- fitted weight+bias scalar count
- layer shapes
- dense weighted-sum terms per scored candidate
- number of candidates scored
- total learned weighted-sum proxy

The learned proxy is not:

- FLOPs measured by hardware
- CPU instructions
- memory traffic
- latency
- joules

Deterministic checker / solver / reconstruction / verification costs remain separate.

## Primary research outcomes

v0.0.33 is informative under all outcomes.

### Positive

A meaningful fraction of oracle compression is recovered while verified retention remains 1.0.

### Mixed

The model proposes useful reductions, but deterministic checking rejects many.

This would show proposal signal but weak authority-free precision.

### Negative

Recovery is near zero while verified retention remains 1.0.

This would mean the v0.0.32 oracle opportunity is not yet learnably discoverable under the fixed small-model / feature contract.

The negative result must be retained.

## KEEP contract

KEEP means the learned-compression experiment is methodologically valid.

Required:

1. train / validation / final full-system signatures are disjoint
2. variable names and row/column order do not encode oracle role
3. candidate enumeration contains every oracle dependency rule
4. learned model receives no oracle candidate labels at inference
5. proposal budget is exactly documented as oracle-cardinality information
6. deterministic checker rejects tampered or invalid reductions
7. every executed learned-compressed result is verified on the original full problem
8. unsafe accepted reduction count is zero
9. learned cost accounting is deterministic and finite
10. all scale cells are populated

Not required:

- any minimum compression recovery
- any solver-work win
- compact certificates
- better wall-clock

## Claim boundary

A positive v0.0.33 result would show only that:

> a fixed small learned candidate scorer can recover some certified compression opportunities in this generated affine-linear family when given the oracle elimination cardinality.

It would not establish:

- learned discovery of globally minimal structure
- learned discovery of k
- domain-general Structural Compression
- natural-language Structural Compression
- end-to-end total-compute superiority
- LLM efficiency
- asymptotic complexity improvement

## Next gate

If v0.0.33 shows meaningful learned recovery, the next experiment should remove at least one oracle scaffold.

Preferred next target:

    learned stopping / retained-dimension prediction

so the system must decide not only **what** to eliminate but also **how far** to compress.


## Post-result diagnostic-control amendment

After the first learned benchmark result was observed but **before merge**, one methodological gap was identified:

> learned recovery is not interpretable without knowing how much recovery comes from the candidate universe plus deterministic checker alone.

The primary endpoint and KEEP contract above are unchanged.

Two additional **diagnostic, not pre-registered primary** controls are therefore added:

1. deterministic random ranking of the same candidate universe,
2. a fixed non-learned heuristic ranking using only:
   - row density,
   - target-column incidence.

Both controls receive the same oracle-cardinality proposal budget B = n-k and the same deterministic checker.

They report:

- verified retention,
- elimination-count recovery,
- exact-oracle-rule recovery,
- fail-closed rejection count.

Because these controls were added after seeing the first learned result, they must be labeled post-result diagnostics in every report. They may challenge the interpretation of the learned result, but they do not retroactively become pre-registered endpoints.
