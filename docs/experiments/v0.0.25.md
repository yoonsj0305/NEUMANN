# v0.0.25 — Durable Attestation Ledger + Use-Time Evidence Revocation

## Question

Can NEUMANN persist lifecycle attestations as auditable evidence and revoke a historical PASS so that an already-running persistent worker loses privilege before its next plugin RPC?

## Motivation

v0.0.24 made persistent reuse depend on exact-artifact behavioral evidence, but the trusted attestation registry lived only in process memory.

That left two gaps:

1. evidence authority disappeared on restart
2. a PASS had no durable revocation history

A third, subtler failure mode appears if revocation is checked only when the worker is created:

    PASS → worker starts → evidence revoked → old worker keeps receiving RPC

v0.0.25 therefore treats lifecycle evidence as **use-time authority**, not a one-time admission ticket.

## Evidence ledger

New component:

    HashChainedAttestationLedger

The ledger is append-only JSONL and records:

- ledger version
- monotonic sequence
- ISSUE / REVOKE action
- plugin ID
- exact manifest SHA-256
- exact attestation SHA-256
- exact conformance-corpus SHA-256
- complete attestation payload on ISSUE
- reason
- predecessor hash
- event hash

Writes are flushed and fsynced before in-memory state advances.

## Current-state reconstruction

On reload the ledger:

1. parses every record
2. requires a contiguous sequence
3. verifies predecessor links
4. recomputes every event hash
5. reconstructs the embedded LifecycleAttestation
6. verifies plugin / manifest / corpus / attestation identities agree
7. reconstructs the latest evidence state for each exact manifest

Mutation, record reordering, broken links, malformed records, and partial corruption fail closed.

## Runtime contract

The public persistent dispatcher now supports a runtime attestation authority.

When one is supplied, every plugin dispatch checks:

    exact manifest authorization
      +
    current exact lifecycle evidence

before sending a plugin RPC.

The same check is repeated before starting a new worker generation.

Therefore an evidence revocation after a worker has already started causes:

    next operation
      → evidence check fails
      → worker killed
      → zero post-revocation plugin RPC
      → PermissionError

The conformance-only bootstrap path intentionally does not require existing attestation authority, because it must measure the candidate before privilege can be granted.

## Freshness semantics

v0.0.25 defines freshness structurally rather than by wall-clock age.

For one exact manifest digest:

- a newer ISSUE supersedes the previous current evidence
- REVOKE makes the current evidence inactive
- a different manifest digest does not inherit old evidence
- restart reconstructs the same current state from the ledger
- an optional trusted expected head detects rollback or truncation relative to that checkpoint

This version does **not** define a time-to-live or periodic re-attestation interval.

## Pre-registered keep gate

Keep the direction only if all of the following hold:

1. an issued PASS survives restart
2. exact-manifest persistent execution succeeds after reload
3. evidence can be revoked after a worker is already running
4. the next execution is blocked
5. post-revocation plugin RPC count is exactly **0**
6. the existing worker is terminated
7. revoked state survives restart
8. record mutation is detected
9. valid-prefix rollback is detected when a trusted expected head is supplied
10. fresh-venv external-wheel execution obeys the same contract

## Security boundary

The hash chain is **tamper-evident**, not self-authenticating and not rollback-proof by itself.

A local attacker who can replace the ledger with an older internally valid prefix can evade local-only detection unless the runtime also has a trusted expected head stored outside the ledger.

v0.0.25 does not provide:

- publisher identity
- signatures
- distributed consensus
- immutable remote storage
- secure clock / expiry semantics
- formal verification of lifecycle behavior
- proof against adaptive malicious trigger behavior
- OS-level capability sandboxing

Lifecycle attestation remains finite-corpus behavioral evidence.

## Relationship to authorization

Authorization and lifecycle evidence remain separate control planes:

    authorization = may this exact plugin artifact execute?
    attestation   = may this exact artifact receive persistent-reuse privilege?

They are deliberately not collapsed into one state bit.

Revoking either authority must fail closed before the next plugin RPC.

## Candidate next questions

After this milestone, the next work should be selected by measured bottleneck rather than version momentum.

Two live tracks remain:

### Structural-intelligence track

Return to the central NEUMANN hypothesis:

> Does representation-first decomposition reduce model compute while preserving problem-solving quality?

The runtime/plugin substrate is now substantially stronger than the original research core. A next milestone should reconnect infrastructure work to representation quality, compute, latency, and generalization measurements.

### Containment track

Threat Model v2 still identifies same-user host capabilities as outside the process-separation boundary.

Candidate control:

    OS-level capability sandbox

This should be pursued only if the experiment requires executing less-trusted external plugin code.

## Decision rule

v0.0.25 should be marked **KEEP** only after CI and fresh-venv evidence satisfy the pre-registered gate above.
