# v0.0.38.1 — Mixed Local + Coupled Harder-Family Gate

Status: pre-registered research specification

## Motivation

v0.0.38 validated the exact 2x2 block compression primitive but failed the
pre-registered H4 local-progress bridge:

    active one-row progress rate = 56.25%
    required                     = 75%

The failed gate remains binding.

The next experiment does not relax H4, retune the frozen one-row pipeline, or
train a model.

Instead it redesigns the family so the old local primitive has guaranteed
useful work before multi-row structure remains.

## Research question

> Can a generated exact family contain both genuine one-row compression and
> genuine coupled multi-row compression such that the frozen local pipeline
> makes broad verified progress but still leaves substantial solver-relevant
> structure for an exact block primitive?

The intended sequence is:

    local compression makes real progress
        ↓
    local primitive saturates
        ↓
    coupled multi-row structure remains
        ↓
    exact block compression removes the residual structure

## Frozen scale grid

Use the existing grid:

    k in {2, 4}
    n in {4, 8, 16, 32}
    n >= k

There are eight cells.

Final-only audit:

    32 systems per cell
    256 systems total

No threshold calibration or learned fitting occurs in v0.0.38.1.

## Mixed family construction

For each system define:

    derived_count = n - k

### No-compression controls

If:

    derived_count = 0

generate only the dense exact core.

### Smallest active cell

If:

    derived_count = 2

generate:

    easy_leaf_count = 0
    coupled_block_count = 1

This cell remains a pure coupled control because two derived variables cannot
simultaneously contain both motif classes.

### All larger active cells

If:

    derived_count >= 4

freeze:

    easy_leaf_count = 2
    coupled_variable_count = derived_count - 2
    coupled_block_count = coupled_variable_count / 2

The count is integral on the frozen grid.

## Easy one-row motif

Each easy derived variable e receives exactly one row:

    e = c + sum_i a_i x_i

where x_i are core variables only.

Generator restrictions:

- target coefficient magnitude = 1,
- core-side coefficients chosen from {-3, -2, 2, 3},
- the easy target appears in no other row,
- easy leaves do not depend on one another,
- coupled blocks do not depend on easy leaves.

Therefore each easy leaf is independently removable by the existing one-row
primitive without symbolic substitution into any retained row.

## Coupled block motif

Each coupled pair y, z receives exactly two rows:

    y + z = f(core)
    y - z = g(core)

with bounded non-unit core coefficients.

As in v0.0.38, each row exposes valid one-row affine identities, but complete
removal of both targets requires a joint 2-row / 2-target solve.

## Surface hardening

Every system applies:

- row permutation,
- column permutation,
- generic variable names v0...v(n-1),
- new deterministic seeds,
- exact integer ground truth.

The final full-system signatures must be unique within v0.0.38.1 and disjoint
from all earlier generated corpora where signatures are comparable.

## Frozen old-family baseline

Carry forward the exact v0.0.37 deployable pipeline without recalibration:

    target-leaf @ 0.10
        ↓
    deterministic checker
        ↓
    Markowitz residual @ 0.05
        ↓
    deterministic checker

No v0.0.38.1 data may change these thresholds or method choices.

## Mixed exact oracle

Generator metadata records only the intended reference identities:

- easy row-target pairs,
- coupled row-pair / target-pair blocks.

The mixed checker must independently re-derive all algebra from the original
system.

### Easy candidate authority

For each declared easy row-target pair:

1. derive the exact AffineCandidate from the original row,
2. require exact candidate algebra validation,
3. reject unknown or mismatched identities.

### Block authority

For each declared block:

1. re-derive the exact 2x2 target coefficient matrix,
2. require nonzero determinant,
3. derive exact Fraction-valued reconstruction rules,
4. reject any algebra mismatch.

### Joint materialization

The mixed oracle removes all certified easy and block source rows and all
certified easy/block targets in one exact reduction.

It must then:

1. construct the retained square system,
2. solve it exactly,
3. reconstruct every eliminated variable from independently checked rules,
4. verify the ORIGINAL full problem,
5. require exact ground-truth equivalence.

Generator metadata never grants execution authority.

## Core ratios

On active examples:

    oracle_elimination_count = n - k

    one_row_elimination_recovery
        = one_row_accepted_eliminations
          / oracle_elimination_count

    oracle_solver_savings
        = baseline_solver_ops - mixed_oracle_solver_ops

    one_row_solver_savings
        = baseline_solver_ops - one_row_solver_ops

    one_row_solver_savings_recovery
        = one_row_solver_savings
          / oracle_solver_savings

    retained_dimension_gap
        = one_row_retained_dimension - k

## Frozen harder-family gates

The H1-H5 thresholds from v0.0.38 remain unchanged.

### H1 — Oracle reaches the declared core

    mean mixed-oracle retained-dimension error = 0

### H2 — Old local pipeline is materially incomplete

    mean one-row elimination recovery <= 0.75

### H3 — Incompleteness matters computationally

    mean one-row solver-savings recovery <= 0.90

### H4 — Old pipeline still makes real progress

    fraction of active examples with
    one-row accepted eliminations > 0
        >= 0.75

This remains an accepted-reduction criterion.

It is not replaced by candidate visibility.

### H5 — Multi-row value is broad

At least 5 of the 7 active scale cells must have:

    mean retained_dimension_gap
        >= 0.5 * coupled_block_count

For the smallest active cell, coupled_block_count = 1.

## Secondary motif checks

These checks do not replace H1-H5.

For every active example require:

- at least one visible one-row affine candidate,
- expected coupled one-row alternatives remain visible.

For every active example with derived_count >= 4 require:

- exactly two declared easy leaves,
- both easy row-target identities exist in the one-row candidate set,
- each easy target has column incidence exactly 1.

These checks distinguish generator drift from the H4 outcome.

## Safety contract

Required:

    frozen one-row verified retention = 1.0
    mixed-oracle verified retention = 1.0
    unsafe one-row reductions = 0
    unsafe mixed-oracle reductions = 0
    no-compression controls remain unchanged

## Family decision

If safety passes and H1-H5 all pass:

    family_status = HARDER_FAMILY_VALIDATED

Then v0.0.39 may compare block discovery/routing methods.

If safety passes but any H gate fails:

    family_status = FAMILY_NOT_HARD_ENOUGH

Do not train a discovery model.

Revise the family again.

If safety fails:

    family_status = INVALID_FAMILY_OR_CHECKER

Repair correctness before any discovery experiment.

## KEEP contract

KEEP means the pre-registered experiment was executed faithfully.

Required:

1. this specification and generator contract are committed before first full
   result,

3. final signatures are unique and disjoint from prior corpora,
4. row and column permutations are active,
5. names are generic,

8. the mixed oracle uses exact arithmetic,

KEEP does not require HARDER_FAMILY_VALIDATED.

## v0.0.39 boundary if validated

Do not assume a learned block scorer.

First-class discovery baselines must include at least:

1. deterministic exact 2x2 algebraic enumeration,
2. graph / connected-component row-target pairing,
3. sparse row-pair heuristics,
4. the frozen one-row pipeline as the cheap first stage.

A learned block scorer may be added only if these cheaper methods leave
pre-registered downstream solver-work headroom.

The objective remains verified downstream compute, not generator-label
imitation.

## Claim boundary

A passing v0.0.38.1 would support only:

> on a generated exact mixed structural family, the frozen one-row compressor
> makes broad verified progress but leaves substantial solver-relevant coupled
> structure that an exact multi-row block primitive can safely remove.

It would not establish:

- learned block discovery,
- domain generality,
- natural-language Structural Compression,
- global minimality,
- total-compute superiority,
- asymptotic improvement.
