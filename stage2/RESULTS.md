  - 덧셈은 끝이 마지막 올림 하나로 정해져 국소적이다. N×1 곱셈도 마찬가지다(마지막 올림, 또는 늘 읽고 있는 d = 0).
  - **값과 무관한 이동만 쓰는 표에서는 불가능하다 (증명 개요, 헤드 수와 무관).** 값과 무관한 이동은 정지, 오른쪽, 왼쪽, 다음 구분자, 처음으로다.
    - 이런 헤드는 한 step에 한 칸 움직이거나, 고정된 기준점(처음, 구분자, 현재 위치)으로 간다.
    - 그래서 답의 k번째 step까지 읽을 수 있는 자리는 기준점에서 k 칸 남짓 안쪽뿐이다. 가운데 자리는 읽을 수 없다.
    - b = 10^(L−1)이고 a = b + Δ인 같은 길이 L의 입력을 만든다. 답은 Δ의 자리다. 아래쪽 자리는 같고, 가운데에 0이 아닌 자리를 0개부터 16^4개까지 둔 입력들을 만든다.
    - 이 입력들은 레지스터 상태 수(16^4)보다 많다. 그래서 프롬프트 끝 레지스터가 같고 그때까지 읽은 기호도 같은데, `<eos>` 시점이 다른 두 입력이 생긴다.
  - 내용 이동(같은 기호의 다음 위치로)을 쓰는 표까지 포함한 증명은 하지 않았다 [추정: 그래도 불가능].
  - **측정:** 1단계 덧셈과 같은 정렬 흐름 표와 손 제어기(답을 늘 len(a)자리로 낸다)는, 답이 a보다 짧은 예제에서만 틀렸다. 모든 세트에서 틀린 수가 짧은 답의 수와 같다.
    - 분포 안 35/1,000, 11–20 12/500, 21–30 3/500, 31–40 3/500, select 41/1,000, 학습 앞 2,000개 49 · 72 · 59.
  - 7.3절의 말로 하면, 헤드 이동은 정렬된 흐름이지만 답의 끝이 국소적으로 정해지지 않는다.
- **참고 (후보 아님, 동결 아님): 답을 len(a)자리로 0 채운 뺄셈 (`subtraction_pad`).**
  - 예: `8 2 3 - 7 =` → `1 2 3 <eos>`. 1000 − 999는 `0 0 0 1 - 9 9 9 =` → `1 0 0 0 <eos>`.
